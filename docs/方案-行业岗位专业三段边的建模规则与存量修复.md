# 行业 / 专业 / 岗位：三段边的建模规则与存量修复

2026-08-20。定下规则、修存量、并让采集侧不再犯。

## 一、规则

```
主路径（绝大多数岗位走这条）
    行业  ←belongs_to←  专业  ←prepares_for←  岗位

兜底路径（仅当岗位确实没有对口专业）
    行业  ←belongs_to←  岗位
```

两条**互斥**：

1. 岗位挂了专业 → 由**专业**去挂行业，岗位**不再**直连行业
2. 岗位确实没有对口专业（职业培训类、纯管理岗、粒度过细的岗位）→ 才直连行业

为什么要互斥：一个岗位同时有两条到行业的路，行业图上就出现两种到达方式，
计数按哪条算都对不上（`major_count` 与 `occupation_count` 之前就各按一条路数，
「互联网/AI」下 274 个岗位显示 0）。而且「这个岗位有没有对口专业」这件事本身
就该由边的形态表达，不该藏在别处。

## 三、A 类 961 个岗位：判断的是「该走哪条路」

一开始我把判断对象搞错了，以为「有专业就该走专业路径，删掉直连边就行」。
不对 —— **那条 `prepares_for` 边本身也可能是硬凑的**。抽样 BOSS 岗位的对口专业：

```
动漫制作技术      → 动画设计            对口
半导体工艺与装备   → 数字IC验证工程师     对口
现代物流管理      → 供应链经理          对口
大数据管理与应用   → 总裁/总经理/CEO     ✗ 没有专业培养 CEO
柔性电子技术      → 电池工程师          △ 关联很弱
大数据技术应用    → 自然语言处理算法      △ 更对口的是「人工智能技术应用」
```

4465 条 `ai_inferred` 的专岗边里混着这类。所以真正要判断的是一件事：

> **这个岗位有没有真正对口的学历专业？**

| 判断结果 | 专业→岗位边 | 岗位→行业直连边 | 还要做什么 |
|---|---|---|---|
| 有对口专业 | 保留 | **删** | 确保该专业挂到了对应行业（缺则补） |
| 没有对口专业 | **删**（硬凑的） | 保留 | 无 |

这样两条路径天然互斥，不需要额外协调。

### 怎么判断

先用岗位性质做粗分（不用问模型的部分）：

- **管理序列**：总裁/CEO、副总裁、区域负责人、创意总监 —— 从下级岗位晋升而来，
  没有哪个专业直接培养。走直连。
- **特种作业 / 职业培训类**：铲车司机、足疗师、发型师、养发师 —— 有职业技能等级
  认定，但不是学历专业。走直连。
- **粒度过细的派生岗**：家具拆单员、其他医生职位 —— 是某岗位的细分，不是独立培养口。
  走直连。

其余的逐个判断「当前挂的这个专业对口吗」，三种结论：

- `keep`：对口，走专业路径
- `drop`：不对口，删专岗边、走直连
- `uncertain`：判不准 → **用检索核实**，不猜

`麻醉科医生`→麻醉学、`日语教师`→日语、`环保工程师`→环境工程 属于 keep 且当前缺边，
要补；`总裁/总经理/CEO`→大数据管理与应用 属于 drop。

### 专业→行业边怎么补（判 keep 之后）

**不能机械推导**。试过「岗位直连行业 I + 专业 M 对口该岗位 → 给 M 挂上 I」，
一跑 6334 条新边、每个专业平均挂 6 个行业 —— 又是一次机械对齐，和
「广告设计师 → 体育」同一个毛病（那批就是「给每个行业硬凑 12 个岗位」凑出来的）。

判据要落在「这个专业本身属于哪个行业」，与岗位无关。参考依据：
教育部专业目录的**所属专业大类**（`attrs` 里有 `catalog` / `discipline`），
它到 BOSS 行业的映射是有限的多对多，可以人工核一遍（19 个专业大类 × 149 个行业，
一次性工作），之后所有专业按大类继承，比逐专业猜可靠得多。

## 四、国标岗位那 1159 条行业边：归档，**并登记重做**

这批不参与上面的判断，它整体是错的：关键词机械对齐的产物 —— 每个行业整整 12 个
岗位、每个岗位平均挂 6.3 个行业，跑出「广告设计师 → 体育」「包装设计师 → 体育」。

处置是归档（`archived`，可恢复），不是删。但**归档不是终点** ——
归档之后国标 1331 个岗位里那 306 个会从行业图消失，等于把「行业→国标岗位」
这条链路整段拿掉了。所以必须同时把重做登记成待办，见第七节。

⚠ 这个项目已经吃过一次「处理完就忘」的亏：2026-08-14 手工回填 8919 个技能档位，
08-18 有人重灌库把它盖回去，全程零报错，直到抽查才发现数字逐位退回。

## 五、执行清单（全范围，不试点）

961 个 A 类 + 111 个 C 类 + 165 个 B 类校验，一次做完。分步可回滚。

| 2 | `judge_occupation_major_fit.py` | 全部 961 A 类 + 111 C 类逐个判定 `keep`/`drop`/`uncertain`，产出 json，**不写库** | — |

| 4 | `apply_occupation_path_fix.py --apply` | 按判定结果落库：`drop` 删专岗边、`keep` 删直连边 | 是（归档而非物理删） |
| 5 | `derive_major_industry_by_catalog.py` | 按**专业大类 → 行业**映射表补专业→行业边 | 是 |

第 2 步为什么不写库：判定结果要能被人翻看和修正。961 条判定里必然有错的，
先落成 json、抽查过再落库，比直接改完再回滚省事。

第 5 步的映射表（19 个专业大类 × 149 个行业）是**一次性人工核对**的产物，
落在 `data/mapping/major_catalog_to_industry.json`，进 git。之后所有专业按大类
继承 —— 这是唯一能避免「每个专业挂 6 个行业」的做法，逐专业猜必然发散。

验收：
- 闸门 `verify_industry_path_exclusive.py` 通过（同时有两条路径的岗位数 = 0）
- 行业图上随机抽 10 个行业，专业层与岗位层都有内容
- `搜索行业` 下拉里的 `major_count` / `occupation_count` 与库内一致

# 前后台完整能力对照 · 数据建模缺口（先建模）

> 日期：2026-08-06  
> 需求原文：前台学员端（探索 / AI 双通道诊断 / 学习路径与进度 / 成就游戏化）；后台管理端（模型维护 / 技能库与图谱 / AI 辅助建模 / 审核发布 / 资源权限 / 运营看板与校验演进）。  
> 参考产品：`https://fad9b1015ce041ae9dd149363f74c632.gz2.agentos-app.net`  
> 当前仓库能力中心：**知识图谱底座（KG）+ 简易 Admin 探索 + 规划工作台壳**，**不是**完整 toC/toB 产品。

---

## 0. 一句话结论

| 层次 | 结论 |
| --- | --- |
| **领域知识图（行业/专业/岗位/技能…）** | **有骨架、可溯源、可查询**；覆盖与边质量仍有缺口 |
| **产品运行时模型（用户、诊断、路径、进度、成就、审核流）** | **基本未建模**；库内无用户态表，仅有 KG 的 nodes/edges |
| **与需求产品的差距** | 当前 ≈「内容与关系底座」；需求 = 底座 **+** 用户成长域 **+** 运营治理域 |

下文**优先分析数据建模**：先有对象与关系，再谈页面与 Agent。

## 3. 数据建模缺口（按优先级）

### P0 · 支撑「探索专业岗位」的领域图补强（已有，要做扎实）

本期四维目标下，产品探索仍依赖：

| 模型点 | 现状 | 缺口 |
| --- | --- | --- |
| **行业** | Boss 树 149 | 非国标；与专业缺官方边；岗→行业关键词噪声 |
| **专业** | 2281 | 覆盖可；与行业边缺失 |
| **岗位** | 1639 | 有 low 档标签；部分与技能未连 |
| **技能** | 8919 | 解析质量不均；岗覆盖约 30% |
| **专→岗** | 59.6% 专业 | 普本更弱；AI 边未审核 |
| **岗→技** | 29.8% 岗位 | 标准对齐码/名失败项 |
| **技能可教性** | taught_by 几乎空 | 无学习路径就无法「落到资源」 |

**建模动作（领域层）：**

1. 固化四维主链：`industry` ↔ `occupation` ↔ `skill_level`，`major` → `occupation` → `skill_level`  
2. 补 `major —belongs_to→ industry`（或 `serves`）  
3. 技能节点 attrs 统一：`skill_name / scale / level_code / occupation_code`  
4. 边状态机：`confidence` + `attrs.review_status` ∈ {pending, approved, rejected}（**先规范字段，再上表**）

### P0 · 用户与诊断（学员端核心，**整域缺失**）

建议最小可闭环 ER（逻辑模型）：

```
User
  id, role(student|admin|…), profile_json, created_at

UserSkillProfile          # 当前技能画像
  user_id, skill_level_id | skill_name+level, score, source(resume|chat|self), updated_at

DiagnosisSession
  id, user_id, channel(resume|chat), target_occupation_id?, status, created_at

DiagnosisResult
  session_id, gap_json, matched_occupation_ids[], evidence_json, confidence

ResumeAsset
  id, user_id, file_url, parse_json, parsed_at

ChatSession / ChatMessage
  session_id, role, content, tool_calls_json, created_at
```

**与 KG 的连接点：**

- `UserSkillProfile.skill_level_id` → KG `skill_level`  
- `DiagnosisResult.target/matched occupation` → KG `occupation`  
- 差距算法输入：`occupation -requires→ skill_level` **vs** `UserSkillProfile`

**没有这张表，双通道诊断只能是「一次性对话」，无法沉淀画像与复盘。**

### P0 · 学习路径与进度（学员端闭环，**整域缺失**）

```
LearningPath
  id, user_id, diagnosis_id, target_occupation_id, status(draft|active|done)

PathStep
  id, path_id, seq, step_type(course|practice|credential|project),
  ref_node_id?,   -- 可挂 KG course/credential/skill
  title, est_hours, status

UserProgress
  user_id, path_id, step_id?, skill_level_id?,
  progress_pct, last_event_at
```

**依赖 KG：** `skill_level -taught_by/related_to→ course`，`occupation -related_to→ credential` 等。  
**现状：** 课目标多、可学资源弱 → **路径生成模型有「目标技能」无「可执行资源」** 会空转。

### P1 · 成就与游戏化（**整域缺失**）

```
AchievementDefinition  # 配置：完成诊断、首条路径、连续7天…
UserAchievement
PointsLedger           # 增减流水
UserLevel / Streak
```

与 `UserProgress`、`DiagnosisSession` 事件挂钩；**可不进 Neo4j**，进业务库即可。

### P1 · 后台治理（审核发布 / 权限 / 校验）

```
AdminUser / Role / Permission

ModelProposal            # AI 或人工提出的节点/边变更
  proposal_type(node|edge), payload_json, confidence, status

ReviewDecision
  proposal_id, reviewer_id, decision, comment, decided_at

PublishBundle
  id, version_tag, node_ids/edge_ids 快照, published_at, publisher_id

ValidationRule / ValidationRun
  rule_id, severity, result_json, run_at
```

**现状映射：**

- 离线 `link_*` 输出 ≈ 简陋的 `ModelProposal`（但写死进主库）  
- 需要：**提案表 → 审核 → 再写入主 KG**，而不是脚本直写 production edges

### P2 · 运营看板

```
AnalyticsEvent  # view_major, start_diagnosis, complete_path_step…
DailyMetric     # 覆盖率、DAU、诊断完成率（可物化视图）
```

当前 `reports/*覆盖率*` 是 **离线文件**，不是产品看板数据模型。

## 4. 推荐：双库分层（建模原则）

| 库 | 存什么 | 技术建议 |
| --- | --- | --- |
| **KG 库**（已有 SQLite+Neo4j） | 行业/专业/岗位/技能/课/证 + 官方/审核通过的边 | 只放「世界知识」 |
| **业务库**（新建） | 用户、诊断、路径、进度、成就、审核、权限、埋点 | Postgres/SQLite 业务 schema |
| **对象存储** | 简历文件、导出报告 | OSS/本地 |

**禁止**把 `User`、进度打进 Neo4j Entity 与行业节点混在一起（难权限、难合规、难演进）。

**允许**在业务库存 `ref` 到 KG 的 `node.id`。

## 6. 建模落地顺序建议（只谈数据，不排完整排期）

### 第一刀：领域图「四维可算」

1. 规范 `industry / major / occupation / skill_level` 主链与 attrs  
2. 边审核字段统一 + 拒绝脚本直写生产（提案表可第二刀）  
3. 覆盖率指标固化：专→岗、岗→技、岗→行业  

→ **支撑：探索 + 技能差距计算输入**

### 第二刀：诊断与画像

1. `User` + `UserSkillProfile` + `DiagnosisSession/Result` + `ResumeAsset`  
2. 诊断结果 JSON Schema（gap 列表：skill_id, required_level, user_level, priority）  

→ **支撑：双通道诊断持久化与报告**

### 第三刀：路径与进度

1. `LearningPath` / `PathStep` / `UserProgress`  
2. 步骤可引用 KG `course`/`credential`/`skill_level`  

→ **支撑：个性化路径（资源仍可先链检索页/课目标）**

### 第四刀：治理与游戏化

1. `ModelProposal` + `ReviewDecision` + `PublishBundle`  
2. `Achievement*` + 积分流水  
3. `AnalyticsEvent`  

→ **支撑：审核发布、运营看板、成就体系**

## 7. 对参考站点的建模启示

参考前后台若包含「诊断 / 路径 / 进度 / 审核 / 看板」，其背后一定是 **KG + 用户态 + 工作流** 三套模型。  
当前仓库只做了 **KG 第一套**；把参考站完整复刻前，必须先补 **用户态与工作流**，否则只能继续堆节点数，产品能力仍跳不起来。

> 按计划留到观察期后。实施中对预生产做了契约反推，与对接文档有出入，见下方「实测契约修正」。

## 实测契约修正（以真实服务端 422 为准，不以文档为准）

用「有效签名 + 故意的非法值 → 读对方 422 的 `detail`」反推，不写脏数据。
发现文档与实际有三处不一致，其中第一条不改必吃 422：

| # | 文档写的 | 实际契约 | 后果 |
|-|-|-|-|
| 1 | `resources[]` 用 `name` / `source_url` | **`title` / `url`** | 对方 `extra=forbid`，按文档写整条路径被拒 |
| 2 | id 字符集只给了正则 | 同正则，且**总长 ≤128**：`^[A-Za-z0-9][A-Za-z0-9_.:-]{0,127}$` | 技能名带中文/引号（`“互联网+”增材制造`）不能直接当 id |
| 3 | Σ`phase_weight` ∈ [99,101] | 服务端**不校验**（单阶段给 30 也收） | 本地校验器是唯一防线，不能省 |

其余实测约束：`phases` 至少 1 项；`resources[].url` 必须绝对 http(s)；
`job_name` ≤256；`total_duration` ≤64；`phase_name` / `skill_id` / `skill_name` / `task.name`
均 min_length=1；`estimated_minutes` ≥0；`task_weight` >0（因此整条路径不传它）。
这些全部编码进 `backend/learningplan/schema.py`，并由 `tests/unit/test_learningplan_builder.py` 锁住。

## 实施中修掉的一个既有 bug

移植编排算法时发现原 `generate_path._prio()` 用 `gaps[].skill_name` / `gaps[].skill_id`
判断某技能是不是短板，而诊断报告的 gaps 项**根本没有这两个键**（实际是 `skill_key`）。
于是 `is_gap` 恒为 1，「短板优先」一直没生效，排序退化成纯权重序。

修完后同一个岗位（汽车维修工 session 19）选出的 8 个技能从「一半是已达标项」变成
「7 个是实际短板」。另外「已达标」的判定也修了：达标项在报告的 `items` 里，
`gaps` 只装未达标项，从 gaps 里找 `ok=True` 永远是空集；且 `scorable` 是无基准改造时
才加的字段，**历史报告里是 `None`**，按真值判会把所有老报告的达标项误判成未达标。

## 0. 已定的改造原则

1. **接入真实服务，删掉 mock 与本地版**：不保留兜底、不保留双实现；
2. **入口唯一**：生成学习计划只有一条路径、一个接口；
3. **契约以真实服务端为准**：原有 payload 与之不符的，按真实契约**重新设计接口**，不做兼容层；
4. **旧代码清除**：不留死表、死路由、死模型、无触发源的成就。

因此本文第 3 节的删除清单是主体工作，映射与新建（第 4、5 节）反而是小头。

## 4. 契约映射（以真实 payload 为唯一基准）

### 4.1 幂等键重选：用 `session_id`

A 线删除后 `biz_learning_path.id` 不复存在，`external_path_id` 需要新的确定性来源。**用诊断会话 id**：

```
external_path_id = f"vockg-{KG_REGION}-s{session_id}"
```

契约字符集 `^[A-Za-z0-9][A-Za-z0-9_.:-]*$` 满足。这个选择同时解掉三个要求：

- 一次诊断 = 一条路径，**重新测评天然产生新 id**，正合契约"重新测评必须换新 ID"；
- 同一 session 重复调用 → 幂等命中，`created:false`，无副作用；
- 换代：`revision_of_external_path_id` 取该 `(user_id, occupation_id)` 上一条已推送记录的 `external_path_id`。

**连带结论：`session_id` 从可选参数变为必填。** 语义上更清晰——学习计划必须基于一次真实诊断，"没测评就生成计划"这条路本就不该存在。`occupation_id` 不再由客户端传，从 `biz_diagnosis_session.target_occupation_id` 取，消除两者不一致的可能。

`session_id` 无需任何"计算"：它是 `biz_diagnosis_session.id`（`biz_ddl.py:98`，`BIGSERIAL PRIMARY KEY`），建会话时由 PG 自增生成，前端已经持有（`d.assessment.session_id`）。当前前端传的是 `rep.session_id || null`，靠服务端 mock 兜底才没暴露问题，见 3.8。

**`external_path_id` 的构造规则不对外暴露**——不写进 Swagger、不写进 `docs/API接口文档.md`。它只在本服务与 e-ai-spaces 之间流转，前端既不构造也不解析。保持这个性质，将来改构造方式（换前缀、加租户维度）才不会被既有调用方绑住。

### 4.2 字段对应

| 契约字段 | 来源 |
|-|-|
| `external_job_id` / `job_name` | session 的 `target_occupation_id` / 岗位节点 `name` |
| `title` / `goal` | 「{岗位名} 岗位自适应攻关路径」/ 缺省取 `job_name` |
| `total_duration` | Σ`estimated_minutes` 换算「约 N 周」（`_DURATION_BY_LEVEL` 是估算值，非真实课时） |
| `phases[].external_phase_id` / `phase_name` | `stage-{n}` / 技能大类名 |
| `phases[].phase_weight` | 阶段内技能权重之和归一到 100，见 4.3 |
| `tasks[].external_task_id` | `s{session_id}-t{序号}` —— 契约要求全路径唯一，且是前端进度锚点，必须在同一 session 内稳定可重算 |
| `tasks[].name` / `description` | 「补齐技能：{skill_name}（目标 {档位名}）」；档位名只能从 `skill_level_meta` 读，禁止硬编码 |
| `tasks[].estimated_minutes` | `_DURATION_BY_LEVEL[required_level]`，clamp 到 0..6000 |
| `tasks[].skills` | `{skill_id, skill_name}`，≤10 |
| `tasks[].resources` | `_courses_for_skill_key` 的课程名 + `source_url`；**仅 http/https、≤1024、空值丢弃** |
| `tasks[].completed` | 见 4.4 |
| `Userid` 头 | `AuthUser.user_id`（UC MAC Token 校验后的真实 user id；旁路时 `DEV_USER_ID="0"`，符合契约正则） |

### 4.3 权重归一（必须新写）

契约要 `0 < phase_weight ≤ 100` 且 **Σ ∈ [99,101]**；库里 `weight` 是岗位技能权重（Σ≈1），且 A 线给课程步写的是 `0.0`（`biz_store.py:1621`，避免同一技能重复计权）。规则：

- 阶段权重只累加技能任务的 weight，按 `w_i / Σw × 100` 归一；
- 前 N-1 阶段 `round(x, 2)`，**最后一阶段取 `100 - 已分配`**，保证 Σ 精确落在区间内；
- Σw 为 0 的退化情况（脏数据，`as_weight` 有单值守卫但可能整列为 0）→ 阶段间**均分**，否则会推出 `phase_weight=0` 被 422；
- `tasks[].task_weight` **整条路径都不传**，让服务端按"阶段权重在阶段内均分"处理。课程任务 weight=0 违反契约 `task_weight > 0`，混传语义不明确。

### 4.4 `completed` 的语义（待产品确认）

编排取的是岗位全部技能（短板优先排序后截 8），其中一部分是诊断**已达标**的。契约中 `completed: true` 定义为"诊断认定已达标的任务"，据此首次导入就应把已达标任务置 `true`。

这会让学员在 e-ai-spaces 首屏即看到部分进度。符合契约语义，但改变观感 —— 需产品确认。若确认「首次全 false，仅换代结转」，则改为仅在有 `revision_of_external_path_id` 时按 `skill_key` 映射旧路径的完成态。

### 4.5 上限兜底

| 契约 | 现算法产出 | 处置 |
|-|-|-|
| `phases` 1..12 | ≤8（大类去重数） | 断言 + 超限合并尾部阶段 |
| 每阶段 `tasks` 1..50 | ≤16 | 断言；**空阶段必须剔除**否则 422 |
| 全路径 tasks ≤200 | ≤16 | 断言 |

`extra=forbid`：payload 必须严格白名单构造，不可 dump 内部行对象。

### 5.3 409 陷阱与重试规则

契约的 409 是**同 `external_path_id` 但内容变化**。现实触发场景：推送超时 → 重试之间图谱数据或诊断报告变了（如岗位技能权重被运营改过）→ 重算出的 payload 不一致 → 409。

**规则：重发必须用当时的快照，不能重新构造。** `payload_sha256` 用于校验；快照本体建议存 JSONB 列或按 session 确定性重建后比对指纹。构造函数必须是**纯函数且输入固定**（session 的诊断结果一旦落库就不再变），这是幂等性的前提。

碰到 409 时不重试、不改 id 重推，直接记 `push_status='failed'` + `last_error` 并透出——它表示契约违规，需要人工看是谁改了数据。

### 5.4 接口重新设计

```
POST /v1/student/goal/learning-plan
  body: { session_id: int（必填）, recommend_resources?: bool = true }
  200:  { plan_id, external_path_id, created, superseded_plan_id,
          phases_count, tasks_count, pushed_at }
  400:  session 不属于当前用户 / 该 session 无诊断结果
  409:  契约违规（同 path_id 内容变化）
  422:  本地校验未通过（正常不应出现，出现即 builder 有 bug）
  502:  上游 e-ai-spaces 不可用或返回 5xx
```

移除的入参：`occupation_id`（从 session 取）、`gap_skills`（服务端从报告取，不信客户端）。
移除的出参：`source`、`upstream`、`gap_skills`。

#### `session_id` 的三重校验

必填之外还要校验状态。原因是 **`biz_diagnosis_session` 有三个创建入口，但 `biz_diagnosis_result` 不一定有**：

| channel | 创建于 | 是否必然产出诊断结果 |
|-|-|-|
| `assessment` | `create_assessment_session`（`biz_store.py:1085`） | 完成答题并出报告后才有 |
| `resume` | `_persist_resume_diagnosis`（`:927`） | 建会话时同步写入 |
| `chat` | `create_chat_session`（`:1187`） | 对话跑完才有 |

`biz_diagnosis_result.session_id` 是 PK + FK（一对一），拿 `session_id` 不等于拿得到短板数据。三个条件缺一都不能推送：

| 校验 | 失败响应 | 理由 |
|-|-|-|
| session 存在且 `user_id` 为当前用户 | **404** | CLAUDE.md 约定：能被外部拿到的自增 id，不存在与越权同样处理，不泄漏 id 是否存在 |
| 该 session 有 `biz_diagnosis_result` | **400** | 属于状态问题而非找不到。放过去会构造出没有短板数据的空路径，被对方 422 拒——错误暴露在上游，排查成本高得多 |
| `target_occupation_id` 非空 | **400** | 它是 `external_job_id` / `job_name` 的唯一来源，为空则 payload 必然不合契约 |

前两项也是 `tests/e2e_robustness.py` 的注入目标（越界 / 错类型 / 他人 id），改完必须跑。

`GET /v1/student/goal/learning-plans` 保留，返回值补 `external_path_id` / `push_status` / `created_at`。

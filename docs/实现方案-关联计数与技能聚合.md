# 实现方案：关联计数 · 岗位行业 · 技能 L 分存与聚合查询

> 日期：2026-08-06  
> 范围：前台学员 API + 图检索 API；技能存储/查询模型；与管理端编辑约定对齐  
> 前提：技能 **按 L1–L5 分节点存储**（已确认）；列表/详情 **服务端聚合**，前端不自行 group

---

## 1. 目标

| # | 需求 | 验收口径 |
| --- | --- | --- |
| A | 每个节点可展示关联节点数量 | 列表/详情响应带 `counts`，前端直接渲染数字 |
| B | 专业：岗位数、技能数 | `counts.occupation` / `counts.skill`（技能为**逻辑技能**数，见 §3） |
| C | 岗位：所属行业 + 技能数 | `industries[]`（多选）+ 原型取 `[0]`；`counts.skill` |
| D | 行业：关联专业数、岗位数 | `counts.major` / `counts.occupation` |
| E | 技能按 L 分存，查询可聚合 | 新增「逻辑技能」聚合读接口/模式；`skill_count` 按逻辑技能计 |

非目标（本期不做）：改成「一条 skill 节点 + levels JSON」写模型；前端本地 group。

## 2. 图关系与计数语义（published only）

学员端只统计 `kg_node.status = published` 且边 `status = published`（或空=已发布）的关联。

| 主体 type | 计数键 | 图路径 | 去重规则 |
| --- | --- | --- | --- |
| **industry** | `major` | `major -belongs_to→ industry` | `DISTINCT major.id` |
| **industry** | `occupation` | `occupation -belongs_to→ industry` | `DISTINCT occupation.id` |
| **major** | `occupation` | `major -prepares_for→ occupation` | `DISTINCT occupation.id` |
| **major** | `skill` | `major -prepares_for→ occ -requires→ skill_level` | **`DISTINCT skill_key`**（§3） |
| **major** | `industry`（可选） | `major -belongs_to→ industry` | 列表可不返，详情可带 `industries[]` |
| **occupation** | `skill` | `occupation -requires→ skill_level` | **`DISTINCT skill_key`** |
| **occupation** | `major`（可选） | `major -prepares_for→ occupation` | 详情可用 |
| **occupation** | 行业展示 | `occupation -belongs_to→ industry` | 多条 → `industries[]`，FE 取首 |
| **skill_level** | `occupation` | 逆 `requires` | 详情/聚合视图 |
| **skill_level** | `major` | 逆 `requires` + 逆 `prepares_for` | 可选 |

### 2.1 行业子树（可选增强，二期）

若产品要「父行业含下级岗位数」，对 `parent_of` 闭包汇总。  
**本期默认：只计直连 `belongs_to`**，避免口径争议；文档与 OpenAPI 写明。

### 2.2 边方向（实现时写死，勿猜）

```
industry  ←belongs_to—  major | occupation
industry  —parent_of→   industry
major     —prepares_for→ occupation
occupation—requires→    skill_level
skill     —prerequisite_of→ skill   （先修，逻辑技能维度，见 §4）
```

当前 CN 量级约：`belongs_to` ~1.1k、`prepares_for` ~7k、`requires` ~10k，**列表页用一批 SQL 聚合即可**，不必先上物化表。

## 3. 技能：L 分存 + 服务端聚合

### 3.1 写模型（不变）

- 节点 type 仍为 `skill_level`，一条 = 一个技能的一个等级。  
- `name`：`{skill_name} · {level_zh|L码}`  
- `attrs` 扩展：

```json
{
  "skill_name": "流量承接",
  "skill_key": "流量承接",
  "scale": "l1_l5 | mohrss_5",
  "level_code": "L3",
  "level_zh": "熟练",
  "level_int": 3,
  "level_descriptions": {
    "L1": "…", "L2": "…", "L3": "…", "L4": "…", "L5": "…"
  },
  "source_file": "…",
  "occupation_code": "…"
}
```

说明：

- **`skill_key`**：聚合主键。优先 `attrs.skill_key`；缺省回落 `attrs.skill_name`；再回落解析 `name` 中 ` · ` 前半段。  
- **`level_descriptions`**：可冗余写在每个 L 节点（同源同步），或只写在「锚点等级」上；聚合读时 **merge 五档文案**（非空覆盖）。  
- 国标五级：仍 5 条节点；映射 L1=五级/初级工 … L5=一级/高级技师（与产品自评方向一致）。

### 3.2 读模型：逻辑技能 `SkillBundle`

聚合后对外统一形态（学生端 / 管理端列表默认用此形态）：

```json
{
  "id": "bundle:CN:流量承接",
  "type": "skill",
  "skill_key": "流量承接",
  "name": "流量承接",
  "levels": [
    {
      "level_code": "L1",
      "level_int": 1,
      "level_label": "了解",
      "node_id": "CN:skill_level:…",
      "description": "了解站内外流量入口构成…",
      "status": "published"
    }
  ],
  "level_descriptions": {
    "L1": "…", "L2": "…", "L3": "…", "L4": "…", "L5": "…"
  },
  "available_levels": ["L1", "L2", "L3"],
  "missing_levels": ["L4", "L5"],
  "prerequisites": [
    { "skill_key": "精准投放", "name": "精准投放", "bundle_id": "bundle:CN:精准投放" }
  ],
  "counts": { "occupation": 12, "level": 3 },
  "source_url": null,
  "confidence": "derived"
}
```

规则：

| 项 | 规则 |
| --- | --- |
| `bundle.id` | 稳定伪 id：`bundle:{region}:{skill_key}`（不进 `kg_node` 表） |
| `levels[]` | 按 `level_int` 升序；只含已存在 published 节点 |
| 缺档 | `missing_levels` 列出 1–5 中无节点的档；**不自动造节点**（造档走审核/管道） |
| 岗位要求展示 | 某岗 `requires` 多条 L 时，聚合为 **一条逻辑技能 + `required_level`（最高或权重最大档）** |
| 计数 `counts.skill` | 一律 **`COUNT(DISTINCT skill_key)`**，不是 `skill_level` 行数 |

### 3.3 聚合查询 API（前端零聚合）

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| GET | `/v1/student/skills` | **默认 `view=bundle`**：分页逻辑技能 |
| GET | `/v1/student/skills?view=level` | 兼容：原始 `skill_level` 扁平行 |
| GET | `/v1/student/skills/bundles/{skill_key}` | 单逻辑技能详情（含 L1–L5、先修、关联岗数） |
| GET | `/v1/student/positions/{id}` | `skills` **已是 bundle 列表**，每项带 `required_level` / `weight` |
| GET | `/v1/occupations/skills` | 图检索同步支持 `aggregate=1`（默认 1）→ bundle 数组 |
| GET | `/v1/kg/nodes?type=skill_level&aggregate=1` | 管理列表可选聚合（编辑仍点进单 L 或 bundle 编辑页） |

查询参数约定：

| 参数 | 默认 | 含义 |
| --- | --- | --- |
| `view` / `aggregate` | bundle / true（学生端） | 管理端写操作、审核队列默认 `level` 以免误合并审核 |
| `q` | | 匹配 `skill_key` / `name` / 各档 description |
| `has_level` | | 过滤「至少含该 L」的 bundle，如 `has_level=L3` |
| `occupation_id` | | 仅返回该岗 requires 覆盖到的逻辑技能 |

### 3.4 SQL 聚合示意（PG）

逻辑技能列表（分页总数也按 key）：

```sql
-- skill_key 表达式统一函数，避免三处拷贝
WITH sl AS (
  SELECT n.*,
    COALESCE(
      NULLIF(n.attrs->>'skill_key',''),
      NULLIF(n.attrs->>'skill_name',''),
      split_part(n.name, ' · ', 1)
    ) AS skill_key,
    COALESCE(
      (n.attrs->>'level_int')::int,
      CASE n.attrs->>'level_code'
        WHEN 'L1' THEN 1 WHEN 'L2' THEN 2 WHEN 'L3' THEN 3
        WHEN 'L4' THEN 4 WHEN 'L5' THEN 5 ELSE NULL END
    ) AS level_int
  FROM kg_node n
  WHERE n.type = 'skill_level'
    AND n.region = :region
    AND COALESCE(n.status,'published') = 'published'
)
SELECT skill_key,
       count(*) AS level_count,
       array_agg(id ORDER BY level_int) AS node_ids,
       min(level_int) AS min_l,
       max(level_int) AS max_l
FROM sl
WHERE (:q IS NULL OR skill_key ILIKE :q)
GROUP BY skill_key
ORDER BY skill_key
LIMIT :limit OFFSET :offset;
```

岗位技能聚合：

```sql
-- 对 occupation 的 requires 边，按 skill_key 折叠
-- required_level = max(level_int)；weight = max(weight)
```

专业技能数：

```sql
SELECT count(DISTINCT skill_key)
FROM major --prepares_for--> occ --requires--> sl
WHERE major.id = :id AND 各方 published;
```

### 3.5 先修技能（逻辑层，无环）

- 边：`prerequisite_of`，**端点用逻辑技能锚点**，不绑某一 L：  
  - 方案：**新增轻量表** `kg_skill_prereq(skill_key, prereq_skill_key, …)`，避免 5×5 爆炸；或  
  - 边挂在「代表节点」上（如该 key 最小 `level_int` 的 node_id），读时解析为 key。  
- **推荐轻量表**（清晰、易做无环校验、与 L 节点增删解耦）。  
- 发布/保存时：DFS/拓扑检环；环则 400。  
- 聚合详情 `prerequisites[]` 直接出 key + name，前端只展示。

### 4.1 通用字段

```json
"counts": {
  "major": 0,
  "occupation": 0,
```

按 type **只填有意义的键**（其余 0 或省略）。OpenAPI 写清各 type 必填键。

**行业列表项**

```json
{
  "id": "CN:industry:…",
  "name": "互联网",
  "counts": { "major": 36, "occupation": 120 }
}
```

**专业列表/详情**

```json
{
  "id": "CN:major:…",
  "name": "高专 · 软件技术 · 510203",
  "counts": { "occupation": 18, "skill": 42 }
}
```

**岗位列表/详情**

```json
{
  "id": "CN:occupation:…",
  "name": "数据分析师",
  "industries": [
    { "id": "CN:industry:…", "name": "互联网" },
    { "id": "CN:industry:…", "name": "企业服务" }
```


## 5. 实现分层

```
routes_student / main
    → biz_store / query
        → counts.py          # 批量计数
        → skill_aggregate.py # skill_key 表达式 + bundle 组装
        → prereq store       # 先修表 + 环检测
```

### 5.1 批量计数（禁止 N+1）

列表拿到本页 `ids[]` 后 **一次 SQL**：

```sql
-- 示例：本页专业的岗位数
SELECT e.src_id AS id, count(DISTINCT e.dst_id) AS occupation_count
FROM kg_edge e
JOIN kg_node o ON o.id = e.dst_id
  AND o.type = 'occupation'
  AND COALESCE(o.status,'published') = 'published'
WHERE e.rel_type = 'prepares_for'
  AND e.src_id = ANY(%s)
  AND COALESCE(e.status,'published') = 'published'
GROUP BY e.src_id;
```

技能数（专业）用子查询 + `skill_key` 表达式 `COUNT(DISTINCT …)`。  
岗位行业：`WHERE dst/src … ANY(%s)` 后在 Python 按 id 分组装 `industries[]`。

### 5.2 性能

| 阶段 | 策略 |
| --- | --- |
| 本期 | 在线聚合 + 复合索引 |
| 索引 | `(rel_type, src_id)`、`(rel_type, dst_id)`、`(type, region, status)`；`attrs` 上 `(attrs->>'skill_name')` 表达式索引（PG） |
| 若列表 P99 变差 | 物化 `kg_node_stats(node_id, major_c, occ_c, skill_c, …)`，审核通过/边写入后增量更新或夜间全量 |

### 5.3 能力等级文案数据源（与前议一致）

| 来源 | confidence | 管道 |
| --- | --- | --- |
| 国标 PDF 分等级「专业能力要求」 | official | ingest 扩展写入 `level_descriptions` / 各 L description |
| 无源 | derived / ai_inferred | rubric 或 LLM 草稿 + 发布必填 BR-04 人工确认 |
| 管理台编辑 | manual | 审核通过后写回各 L 节点（同源同步五档文案） |

先修：无权威全库 → 管理台维护 + 可选 LLM 候选；**不爬造**。

## 8. 风险与口径

| 风险 | 处理 |
| --- | --- |
| 同名不同工种 `skill_name` 冲突 | `skill_key` 可升级为 `{occupation_code}|{function}` 或 `source_id` 前缀；展示名仍用短名 |
| 旧数据无 `attrs.skill_name` | 回填脚本 + SQL `COALESCE` 兼容 |
| major→skill 两跳噪声 | 只计 published；可选 `confidence != ai_inferred` 开关后续加 |
| 聚合 id 非真实节点 | 文档标明 `bundle:…` 不可直接 `PATCH /kg/nodes`；编辑 API 走 skill_key 或展开 node_ids |
| 计数与列表 limit 不一致 | counts 为全库关联总数，详情内嵌列表仍可 `limit` |

## 11. 决议摘要

1. **存储**：技能继续 **一 L 一节点**。  
2. **查询**：默认 **逻辑技能聚合**；计数里的技能 = **distinct skill_key**。  
3. **关联数**：服务端批量 SQL，挂在列表/详情 `counts`。  
4. **岗位行业**：边多选，`industries[]` + 服务端展开首项字段。  
5. **先修**：逻辑技能维度表 + 无环；与 L 节点解耦。  
6. **前端**：不 group、不数边；只渲染。

## 12. 写接口：一次录五档 + 权重归属（2026-08-06 补）

### 12.1 档位录入形态：`levels.L1 = {}`（推荐）

**不要**只做 `level_descriptions: { "L1": "纯字符串" }` 作为唯一形态；字符串可兼容，规范形态为对象：

```json
{
  "type": "skill_level",
  "skill_key": "流量承接",
  "name": "流量承接",
  "scale": "l1_l5",
  "occupation_links": [
    {
      "occupation_id": "CN:occupation:…",
      "weight": 0.25,
      "required_level": 3
    }
  ],
  "levels": {
    "L1": {
      "label": "了解",
      "description": "了解站内外流量入口构成…",
      "criteria": [],
      "evidence": null
    },
    "L2": { "label": "掌握", "description": "…" },
    "L3": { "label": "熟练", "description": "…" },
    "L4": { "label": "精通", "description": "…" },
    "L5": { "label": "专家", "description": "…" }
  }
}
```

| 约定 | 说明 |
| --- | --- |
| 键 | 固定 `L1`…`L5`（也接受 `1`…`5`，入库规范成 `L*`） |
| 值 | **对象**优先；若传 string，服务端规范化为 `{ "description": s }` |
| 缺档 | 未出现的键 **不建节点**（允许只录 L1–L3）；产品若 BR-04 必填五档，在校验层拦 |
| 扩展位 | 对象内可加 `criteria` / `evidence` / `examples` / `score_hint` 等，不破坏契约 |
| 拆库 | 每个有对象的 L → 一条 `skill_level`：`name = "{skill_key} · {label|L码}"`，`attrs.skill_key/level_code/level_int/level_zh`，`description` = 对象.description；`attrs.level_payload` 可存整对象 JSON |
| 审核 | 一笔 change 可带 `expand_levels: true`，通过后写 N 节点 + 边；或一笔提案 payload 含 levels，apply 时拆 |

兼容入参（弱）：

```json
"levels": { "L1": "纯文案", "L2": "…" }
```

### 12.2 权重：存在 **岗→技边** 上，不存在技能节点本体

| 问题 | 结论 |
| --- | --- |
| 权重语义 | **该技能在该岗位技能构成中的占比**（国标「技能要求权重表」同义） |
| 存在哪 | **`occupation -requires→ skill_level` 边的 `weight`**（0–1；源表百分比则 /100） |
| 为何不在技能节点 | 同一技能挂多岗时权重不同；节点上的 `weight_pct` 只是历史 ingest 冗余，**读路径以边为准** |
| 为何不在岗位节点 | 岗位上塞 `skills:[{id,weight}]` 会与图边双写、难审核；列表「技能构成」应 **遍历 requires 边** 聚合 |
| 五档怎么挂权重 | **逻辑技能对岗位一个权重**：对 `required_level` 对应那条 L 边写 weight；或五档边写 **相同** weight（展示按 skill_key 取 max/任一条）。推荐：**只在 required 档（或最高已建档）写 weight**，其它 L 边 `weight=null`，聚合展示时用该 skill_key 下非空 weight |

岗位详情展示：

```text
技能构成 = GROUP BY skill_key
  name, required_level, weight(来自 requires 边), levels[]
权重和（可选校验）= SUM(weight) 按逻辑技能，理想接近 1.0（国标表常见百分制）
```

### 12.3 历史数据

- 管道曾把 `weight_pct` 写进 **节点 attrs** 且边上也有 `weight`：以 **边** 为准；节点字段逐步视为只读兼容。  
- 管理创建/编辑：权重只出现在「关联岗位」表格列，不出现在「技能本体」主表单。

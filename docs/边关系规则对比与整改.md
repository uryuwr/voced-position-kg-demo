## 三、对比与差异

| 规则 | 项目实现 | 判定 |
| --- | --- | --- |
| ① 行业→岗位 HAS_OCCUPATION | `occupation→industry` belongs_to（1159，**方向相反**、命名不同） | ⚠️ 方向/命名分歧，语义等价 |
| ② 专业→岗位 PREPARES_FOR | `major→occupation` prepares_for（6939） | ✅ 一致 |
| ③ 岗位→技能 REQUIRES_SKILL | `occupation→skill_level` requires（9938） | ✅ 方向对，仅命名差 |
| ④ 专业→技能 TEACHES_SKILL（核心必须） | **covers=0，无直接边**；实为 `major→course→skill` 间接 | ❌ **核心关系缺失** |
| ⑤ 技能↔技能 RELATED_SKILL | 无 | ➖ 缺失（扩展） |
| ⑥ 岗位↔岗位 RELATED_OCCUPATION | 无 | ➖ 缺失（扩展） |
| ⑦ 行业→行业 SUB_INDUSTRY | `industry→industry` parent_of（134） | ✅ 一致 |
| ⑧ 岗位→认证 REQUIRES_CERT | `occupation→credential` 走 **related_to**（2042），recognized_by=0 | ⚠️ 语义未落到专门边 |
| ⑨ 技能→课程 TAUGHT_BY | taught_by 仅 33；`course→skill_level` 走 **related_to**（7350，**方向反**） | ⚠️ 类型错+方向反 |
| ⑩ 专业→认证 RECOMMENDS_CERT | `major→credential` 走 **related_to**（2186），articulates_to=0 | ⚠️ 语义未落到专门边 |

**规则表未覆盖、但项目实际存在的边：**
- `major→industry` belongs_to（1570）——「专业→行业」，规则表只有行业→岗位、专业→岗位。
- `major→course` related_to（16855）——「专业→课程」，规则表无此关系。
- `course→course` related_to（800）——课程间相关。
- 本体里的 `leads_to`（课→证）、`same_as`（跨库等价）规则表也未列。

## 四、核心问题

1. **`related_to` 被当万能边**：约 **2.9 万条** related_to 混装了 ≥5 种不同语义与方向（专业→课程 1.7万、课程→技能 7350、专业→认证 2186、岗位→认证 2042、课程→课程 800）。违反规则「方向统一、每条边语义明确」，直接影响路径分析与推荐质量。**这是最大偏差。**
2. **规则④「专业→技能」核心关系缺失**（covers=0）：目前只能靠 `专业→课程→技能` 两跳间接得到。
3. **方向/命名口径不统一**：`belongs_to`(岗位/专业→行业) vs 规则 HAS_OCCUPATION(行业→岗位)；`requires/covers/parent_of/recognized_by/articulates_to` vs 规则 REQUIRES_SKILL/TEACHES_SKILL/SUB_INDUSTRY/REQUIRES_CERT/RECOMMENDS_CERT。
4. **规则表本身不全**：缺「专业→行业」「专业→课程」「课程→课程」「课→证 leads_to」「same_as」。

## 五、整改建议（按优先级）

### P0 · related_to 语义化拆分（数据质量核心）
把混在 related_to 里的、语义/方向明确的边，迁移到专门 rel_type：

| 现状（related_to） | 目标 rel_type | 动作 |
| --- | --- | --- |
| course → skill_level（7350） | `taught_by`（skill_level→course） | **翻转方向** + 改类型 |
| occupation → credential（2042） | `recognized_by`（规则⑧ 岗位→认证） | 改类型 |
| major → credential（2186） | `articulates_to`（规则⑩ 专业→认证） | 改类型 |
| major → course（16855） | 需先定关系名（建议新增「专业开设课程 offers_course」或并入 covers 语义） | 定义后迁移 |
| course → course（800） | 保留 related_to 或新增 `related_course` | 视需要 |

> 迁移前先按 `confidence` 抽检（大量应为 `ai_inferred`/`derived`）；可逆，保留原 evidence/source。

### P0 · 补齐规则④「专业→技能」
二选一：
- **建直接边** `major -covers-> skill_level`：可由 `major→course→(taught_by)→skill` 推导生成（confidence=derived，标注来源路径）；或
- 若产品接受「专业经课程中转到技能」，则在规则表④注明「间接路径」，不强建直接边。

### P1 · 统一命名与方向口径
出一份「规则表 ↔ schema」映射表并二选一定稿：
- **推荐**：不物理改 rel_type（`prepares_for/requires/belongs_to/...` 已被 API/前端大量引用，重命名成本高、风险大），而是**更新规则总表用项目实际命名+方向**，规则名作为业务别名（label）。
- 若坚持规则命名，需评估 API/前端/查询全链路改造成本。
- 「行业↔岗位」方向定稿：建议保留 `occupation→industry belongs_to`（子归父的通用建模），规则表①改注方向。

### P1 · 补全规则表
把实际存在的 `major→industry`、`major→course`、`course→course`、`leads_to`、`same_as` 补进规则总表并定义方向/置信度。

### P2 · 扩展关系
`RELATED_SKILL`（技能↔技能）、`RELATED_OCCUPATION`（岗位↔岗位）当前无数据，按推荐/路径分析需求再补；建议独立 rel_type 而非并入 related_to。

### P2 · 认证相关（⑧⑩）
认证节点当前已置 draft 隐藏；待认证数据恢复后，随 P0 的语义化迁移一并落到 `recognized_by`/`articulates_to`。

## 六、属性规范符合度

`kg_edge` 现有字段：`source_system/source_id/source_url/license/fetched_at/confidence/weight/evidence/status/updated_by`。基本满足规则的属性规范（source/confidence/weight/status/evidence 齐全）；`confidence` 取值为 `official/derived/ai_inferred/manual_seed`，与规则「高/中/低」需一份对照（official/derived≈高，manual_seed≈中，ai_inferred 需审核）。

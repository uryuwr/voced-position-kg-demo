## 二、后端接口评估

### 2.1 能直接支撑的

| 需求 | 现有能力 | 结论 |
| --- | --- | --- |
| 行业模糊搜索 + 下拉 | `GET /v1/search?q=&type=industry&limit=` | ✅ 可用 |
| 行业两层树 | `GET /v1/industries/tree`；`parent_of` 134 条、15 个顶层 | ✅ 可用 |
| 行业 → 专业 → 岗位 三层图 | `GET /v1/graph/by-industry`，已有 `industry_id`/`max_nodes`/`include_skills`/`include_direct_occupations` | ⚠️ 基本可用，需调整（见 2.3） |
| 岗位 → 技能（含等级） | `GET /v1/occupations/skills?aggregate=true` | ✅ 可用 |

数据连通性也够：`major -belongs_to-> industry` 覆盖 1570/1936（81%），
`major -prepares_for-> occupation` 6939 条，三层链路完整。

### 2.2 数据缺口（阻塞，非改代码能解决）

| 缺口 | 现状 | 影响 |
| --- | --- | --- |
| **技能分类 `category`** | `kg_node.category` 字段已建，但 **8919 个技能全部为 NULL，零填充** | 线框图 1.5 的分区（运营策略/数据能力/技术工程/通用素养…）**画不出来**，只能退化成一堆无分组的技能 |
| **技能前置关系** | `kg_skill_prereq` 表已建、CRUD 齐全（含成环检测），但 **0 行** | 线框图 1.5 的箭头 `──→` **画不出来** |

这两项是 1.5「技能的分类、前置关系」的全部内容，目前**后端一条数据都没有**。
表结构和写接口都就绪，缺的是数据来源——见第三节 Q1。

### 2.3 建议新增/调整的接口

**新增 `GET /v1/industry-graph`**（三层聚合，替代直接用 by-industry 通用子图）

理由：`by-industry` 返回通用 `GraphResponse`，前端要自己判层、自己截断；
且行业规模差异极大（专业数中位数 12、最大 **292**），必须由后端按层截断并告知截断量。

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `industry_id` | str | — | 行业节点 id（与 `industry` 二选一） |
| `industry` | str | — | 行业名关键字 |
| `include_children` | bool | `true` | 是否把子行业的专业一并纳入（选大类时用） |
| `limit_majors` | int | `20` | 专业层截断，按关联岗位数倒序 |
| `limit_occupations_per_major` | int | `8` | 每专业岗位截断 |
| `layout` | enum | `layered` | `layered`(分层) / `matrix`(热力图) |

响应按层组织，前端不用推断层级：

```jsonc
{
  "industry": { "id": "...", "name": "电子/通信/半导体", "parent": {...} },
  "layers": {
    "majors":      [{ "id": "...", "name": "微电子技术", "occupation_count": 9 }],
    "occupations": [{ "id": "...", "name": "芯片设计工程师", "skill_count": 23,
                      "major_ids": ["..."] }]
  },
  "links": [{ "from": "<industry|major id>", "to": "<major|occupation id>",
              "rel": "belongs_to|prepares_for" }],
  "matrix": {                       // layout=matrix 时才给
    "rows": ["major_id..."], "cols": ["occupation_id..."],
    "cells": [{ "r": 0, "c": 2, "v": 7 }]
  },
  "meta": { "major_total": 76, "major_shown": 20,
            "occupation_total": 117, "occupation_shown": 58, "truncated": true }
}
```

**新增 `GET /v1/occupation-skills-graph`**（技能图谱，供 1.5）

在现有 `occupations/skills` 基础上补两样：`category` 分组 + `prereq` 边。

```jsonc
{
  "occupation": { "id": "...", "name": "芯片设计工程师" },
  "categories": [
    { "key": "技术工程", "skills": [
        { "skill_key": "Verilog", "levels": ["L2","L3"], "level_descriptions": {...} }
    ]}
  ],
  "prereqs": [{ "from": "数字电路", "to": "Verilog", "confidence": "ai_inferred" }],
  "meta": { "skill_total": 23, "uncategorized": 0, "prereq_total": 5 }
}
```

`category` 未填充期间，此接口会把全部技能塞进 `{"key": "未分类"}` 一组，
`prereqs` 返回空数组——前端要能优雅降级（分区退化为单区、不画箭头）。

## 三之前｜数据缺口已填（种子数据，2026-08-10）

三个缺口都已用**可追溯的种子数据**补上，不是凭空 mock。

### 技能分类 `category` — `scripts/seed_skill_taxonomy.py`

原型图那套「运营策略/内容创作」是互联网口径，与库内数据不符：库里 skill_level
全部来自国家职业技能标准（`attrs.standard_type=national_skill_standard`），
技能名形如「生产准备」「故障判断与处理」「安全风险辨识与管控」。

改按国标正文结构「**职业功能** → 工作内容 → 技能要求」中的**职业功能**维度分 10 类：
安全与环保 / 作业准备 / 操作与加工 / 设备维护与检修 / 质量与检验 /
数据与信息 / 服务与业务 / 技术管理与创新 / 运营与管理 / 培训与指导。

覆盖 **7318 / 8919 个 skill_level 节点（82%）**，规则匹配不到的保持 NULL。

> 修正记录：`装药/填塞/起爆/警戒/爆后` 最初归入「安全与环保」，
> 实为爆破作业的操作步骤，已移到「操作与加工」——否则会派生出
> 「爆后检查与处理 → 作业准备」这种方向颠倒的前置关系。

### 技能前置关系 — `scripts/seed_skill_prereqs.py`

**60 条**，每条须同时满足两个约束：

1. **分类白名单**：只在真实的职业功能推进方向上连（如 `作业准备→操作与加工`、
   `技术管理与创新→培训与指导`）。最初用「rank 相邻」，会把同岗位的并列职责
   误连成依赖（曾连出「警情受理与调度指挥 → 搜救犬饲养与管理」），故改为显式白名单。
2. **真实共现**：两技能必须被同一岗位同时要求，共现岗位数写进 `evidence`。

全部通过 `_would_cycle` 无环校验。样例：`生产准备→生产操作`(10 岗位)、
`生产操作→故障判断与处理`(12)、`制作产品→检验产品`(4)、`技术管理→培训指导`(14)。

### 岗位晋升链 — `scripts/materialize_advances_to.py`

已**物化为 kg_edge 真边**（`rel_type=advances_to`、`structure_layer=chain`），
`/v1/capability` 也改为读真边而非运行时派生，晋升关系因此在通用图接口
和管理端里都可见、可编辑、可审核。脚本两种模式：

| 模式 | 依据 | confidence | 产出 |
| --- | --- | --- | --- |
| `ladder`（默认） | 同词干 + 职级后缀阶梯（工/员 → 技术员 → 技师 → 工程技术人员） | `manual_seed` | **13 条**，已入库 |
| `level` | 按 `occupation.level` 分族递进 | `derived` | 21 条，**质量不合格，已回滚** |

`level` 模式的产出被否决，因为 `occupation.level` 是正则 mock 的，错误被放大：
`初级中学教师→中等职业学校教师→高级中学教师`（学段而非晋升）、
`化工单元操作工→化工原料准备工`（方向反）、`教练员/运动员→体育经理人`（并列转岗）。

`ladder` 模式的 13 条是我国「技能人才（工/员）→ 专业技术人才（工程技术人员）」的
真实上升通道，例：`铸造工→铸造工程技术人员`、`消防员→消防工程技术人员`、
`快递员→快递工程技术人员`（人社部 2019 年新职业，正是为快递技能岗打通的技术口）。
数量止于 13 是因为库内只有这些岗位构成真实职级对——**未为凑数编造**。
待企业职级表/招聘级别数据接入并回填 `occupation.level` 后，重跑即可扩量。

## 三、待你确认（Q1/Q3/Q4 已定，见上；Q2 取共有技能数）

**Q1｜技能分类与前置关系的数据从哪来？**
这是 1.5 能否成立的前提。三个选项：
(a) LLM 批量推断（项目已有 AI 网关 `backend/agent/llm.py`），标 `confidence=ai_inferred`，人工抽检；
(b) 爬取权威技能框架（如国标职业技能标准、ESCO 技能层级）后映射；
(c) 先人工维护高频 Top-N 技能（现有管理端 CRUD 已支持），其余留空。
建议 (a) 打底 + (c) 校正——8919 个技能纯人工不现实。

**Q2｜热力图的「强度」定义？**
候选：① 专业与岗位共有的技能数；② 该专业下该岗位的开设/推荐权重（当前 `prepares_for` 边有 `weight` 字段但多为空）；③ 就是 0/1 有无关联（那更适合用矩阵点阵而非热力）。

**Q3｜大类 vs 子行业，用户默认选哪一级？**
选大类（如「互联网/AI」）会把 17 个子行业的专业全并进来，最大能到 292 个专业，图会很挤；
选子行业则规模适中（中位数 12 个专业）。建议：搜索框两级都能搜，但默认引导选到**子行业**；
选中大类时先展开子行业列表而非直接画图。

**Q4｜岗位层要不要保留「晋升链」？**
上一版做的 `advances_to` 晋升链在本设计里没有位置（1.3 只画归属关系）。
可以在岗位节点上加一个「↑晋升」角标，或干脆本期不显示。
提醒：该数据目前几乎为空（岗位源自职业分类大典，无职级维度）。

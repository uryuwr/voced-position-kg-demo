# 根因分析：国标采集丢失的两个维度

> 2026-08-18 · 起因是管理台一个具体疑问：「室内装饰设计师层级是 L2，为何技能要求全是 L5？」
> 顺着查下去，发现四个看起来互不相干的症状同出一源。

## 0. 一句话

国家职业技能标准的正文结构是 **`职业功能 → 工作内容 → 技能要求`**，且整份标准按 **职业等级**（五级/初级工 … 一级/高级技师）分章。采集时只保留了「工作内容 / 技能要求」这一层 —— **父级的「职业功能」列丢了，「职业等级」的语义也丢了**（等级数据还在，但失去了"这是不同等级的不同要求"这个语义，被当成同一岗位的重复数据压平）。

分类、先修方向、职级梯度三件事的数据来源，恰好就是这两个维度。

## 1. 四个症状

| # | 症状 | 实测数据 |
|-|-|-|
| 1 | 技能分类大面积为空 | `skill_level` 共 12062 个，`category IS NULL` 有 **4744** 个；其中 BOSS 来源 **3135 个命中率 0** |
| 2 | 先修关系几乎没有 | `kg_skill_prereq` 全库仅 **60 条**、涉及 37 个技能；BOSS 那批 **0 条** |
| 3 | 国标岗位技能要求一头沉 | 国标 `requires` 边 `published` 中 **L5 占 2202 / 3172（69%）** |
| 4 | 岗位职级无梯度 | 2463 个岗位中 1641 个有 `level`，其中 **1600 个都是 `2`**（97.5%） |

症状 3 是最初的疑问，症状 1、2 是之前排查先修列时发现的，症状 4 是查职级字段时发现的。

## 2. 「职业等级」是怎么被压平的（症状 3、4）

### 2.1 数据其实是齐全的

以「室内装饰设计师」（`CN:occupation:MOHRSS_CN:4-08-08-07`，`level=2`）为例，它的 `requires` 边**实际有 29 条，L1–L5 全都有**，只是低档全被归档了：

```
archived   L1   5        published   L5   6      ← 只有最高档存活
archived   L2   6
archived   L3   6
archived   L4   6
```

全库国标岗位同一形状：`archived` 里 L1–L4 共 **6611** 条，`published` 里 L5 有 **2202** 条。

**低档的边没有被物理删除，恢复得回来** —— 这是修复的有利条件。

### 2.2 国标每个等级都有独立的要求与权重

实测「方案设计」这一个技能在该职业下的 5 个档位节点：

| 档位 | L1 | L2 | L3 | L4 | L5 |
|-|-|-|-|-|-|
| `weight_pct` | 25 | 25 | **30** | 25 | 20 |

权重逐档不同，说明这是**5 套各自完整的要求**，不是同一套的重复副本。

### 2.3 压平发生在两步

**第一步，采集端无条件建边**（`crawlers/cn/ingest_skill_standards.py:804`）：

```python
for n in nodes:
    pending_edges.append((meta, n))     # 每个 (技能, 等级) 节点都建一条 requires 边
```

一个技能 5 档 → 5 条 `requires` 边指向同一个岗位。

**第二步，去重脚本按兜底规则保留最高档**（`scripts/fix_duplicate_requires.py`）：

| 顺序 | 规则 | 在国标这批数据上 |
|-|-|-|
| 1 | 有权重的优先 | **分不出** —— 5 档全有权重（见 2.2） |
| 2 | 取 `fetched_at` 更新的 | **分不出** —— 同一批采集 |
| 3 | 取档位高的（高档覆盖低档） | ← **落到这条兜底，保留 L5** |

### 2.4 去重脚本本身没错，是被套用在了语义不同的数据上

该脚本的设计目标写在自己的 docstring 里，针对的是**重跑残留**那种真重复：

> `.NET Core开发  L2 (weight=None)` ← 旧
> `.NET Core开发  L3 (weight=0.2)`  ← 新

那种场景下「有权重优先」能精确分辨，规则 3 只是极少数情况的兜底。问题在于国标这批数据每档都有权重，**全部落到兜底规则**，于是「保留最高档」从例外变成了通例。

CLAUDE.md 里「同一技能挂多档是数据错误」这条约定是对的 —— 但它的前提是「同一岗位同一要求」，而国标 5 个等级是 5 个不同的要求，前提不成立。

### 2.5 语义层的真正缺口

国标里的五级/四级/三级/二级/一级对应**同一职业的 5 个职业等级**。而图谱里 `occupation` 只有一个「室内装饰设计师」节点，没有按职业等级拆分，所以 5 套要求无处安放，只能全挂在一个节点上，进而被判成重复。

**去重逻辑完全没有参照岗位自身的 `level`** —— 这是关键：岗位明明有 `level=2`，却拿到了最高档的要求。

## 3. 「职业功能」丢失如何连锁出症状 1、2

`backend/kg/pg_store/skill_taxonomy.py` 的 docstring 已经记录了前半句：

> 库内 skill_level 全部来自该标准，**爬取时丢失了职业功能列**，故由技能名规则反推（种子脚本 `scripts/seed_skill_taxonomy.py`）

于是 `category` 只能靠**技能名关键词正则**反推，命中不了就保持 NULL（脚本明确「不硬塞」）。

而 `category` 又是先修关系生成的前置条件 —— `scripts/seed_skill_prereqs.py` 的双重约束之一是「方向必须落在 `PREREQ_ALLOWED_PAIRS` 白名单里」，**而白名单是分类对**（如 `("安全与环保","作业准备")`）。取不到分类就匹配不上任何一对：

```
职业功能丢失 → category 靠正则反推 → 命中不了为 NULL
                                        ↓
                     PREREQ_ALLOWED_PAIRS 匹配不上 → 先修生成不出来
```

**所以症状 1 和 2 是同一条链，不是两个独立问题。** 重跑先修种子脚本不会有任何改变。

### BOSS 那批是另一个问题：体系不匹配，而非丢失

BOSS 来源的 3135 个技能（`llm://voced-kg/boss-skill-chain`）分类命中率为 **0**，但成因不同：`CATEGORY_ORDER` 的取值域是**国标制造业的职业功能**（安全与环保 / 作业准备 / 操作与加工 / 设备维护与检修 …），而 `C#编程开发`、`.NET Core开发`、`Web API开发`、`EF Core使用`、`Git版本控制` 这类互联网研发技能，一个关键词都碰不上。

十个分类里勉强能装的只有「数据与信息」（可放 SQL 数据库开发），其余无处安放。**这不是补几个关键词能解决的** —— 「C# 编程」属于制造业哪个职业功能，在该语义体系里没有答案。

## 4. 影响面

| 受影响处 | 具体表现 |
|-|-|
| 匹配度算分 | 基准全是 L5，学员几乎不可能达标；`level=1` 岗位要求档均值 4.50、`level=2` 是 4.39，**职级与要求档位不相关** |
| 学习计划编排 | `estimated_minutes` 按 `required_level` 估算（`_DURATION_BY_LEVEL[5]=120`），全部顶格 |
| 晋升路径 | 每个岗位都要求专家级，没有递进空间；`advances_to` 仅 137 条、覆盖 1331 个岗位里的 13 个 |
| 管理台技能构成页 | 第一列「先修」对 BOSS 岗位一律显示「无先修」；要求等级一律高亮 L5 |
| 技能图谱分区 | `industry_graph` 按 category 分组，NULL 全落进「未分类」区 |
| 阶段任务树 | `learningplan/builder.py` 按 category 分阶段，纯 BOSS 技能的岗位会退化成单个「未分类」阶段 |

## 5. 修的方向与依赖顺序

### 5.1 职业等级（症状 3）—— 数据在库里，缺规则

需要「**按岗位职级选对应档位发布**」：岗位 `level=2` 就发布产品档 2 的那批边，其余归档。低档边都在 `archived` 里，可恢复。

**但它依赖职级有梯度** —— 而 1641 个有职级的岗位里 1600 个是 `2`。所以即使加了这条规则，绝大多数岗位仍会一律取 L2，只是从「全 L5」变成「全 L2」，区分度并没有回来。

所以先要解决：**岗位职级本身的取值来源**。当前 `level` 是无约束 nullable int，无字典表、无 CHECK（`kg_node` 上唯一约束是主键），97.5% 的值是同一个数字，实质不承载信息。

### 5.2 职业功能（症状 1、2）—— 原始数据丢了

三条路，代价递增：

**① 重新采集，把「职业功能」列抓回来。** 最彻底，`category` 从规则反推变成官方原始字段（`confidence` 可从 `derived` 升到 `official`），先修白名单随之可用。代价是重跑整条国标采集链路，且要处理 PDF 解析的层级还原。

**② 扩展 `CATEGORY_ORDER`，增加互联网研发的职业功能层**（需求分析／编码实现／测试验证／部署运维）。只解决 BOSS 那批。

注意 `skill_taxonomy.py` 顶部注释警告过的一致性约束：`CATEGORY_ORDER` **同时承担两个职责** —— 前端技能图谱的分区排列顺序，以及 `PREREQ_ALLOWED_PAIRS` 的允许方向。插入新分类必须同时想清楚它排在哪、能指向谁，否则「展示顺序」和「先修方向」会互相矛盾。

**③ 让 BOSS 技能留在「未分类」**，前端把它渲染成正常分区而非缺数据。代价最小，但阶段编排会退化成单阶段。

### 5.3 不该动的

`scripts/fix_duplicate_requires.py` 的三条规则**不要改** —— 它对付重跑残留是正确的，且已作为回归闸门（`--dry-run` 发现重复返回非零退出码）。要改的是**别把国标多等级数据喂给它**：在建边阶段就按岗位职级选档，而不是先全建再去重。

## 6. 遗留的记录缺口

`skill_taxonomy.py` 的 docstring 记录了「职业功能丢失」，但**「职业等级被压平」这件事没有任何地方记录**。这次是靠 `status` 过滤条件的差异（带 `published` 得 6 条全 L5、不带得 29 条 L1–L5）才偶然发现的 —— 换个人查会重复踩一遍。

建议在 `ingest_skill_standards.py` 的建边处、以及 `fix_duplicate_requires.py` 的规则 3 旁各加一句交叉引用，指向本文。

## 附：复现用的查询

```sql
-- 症状 3：某岗位 requires 边的 status × 档位
SELECT COALESCE(e.status,'published') st, n.attrs::json->>'level' lv, count(*)
FROM kg_edge e JOIN kg_node n ON n.id=e.dst_id AND n.type='skill_level'
WHERE e.src_id='CN:occupation:MOHRSS_CN:4-08-08-07' AND e.rel_type='requires'
GROUP BY 1,2 ORDER BY 1,2;

-- 症状 4：职级与要求档位的相关性
SELECT o.level occ_level, round(avg((n.attrs::json->>'level')::numeric),2) avg_req, count(*) edges
FROM kg_edge e
JOIN kg_node o ON o.id=e.src_id AND o.type='occupation'
JOIN kg_node n ON n.id=e.dst_id AND n.type='skill_level'
WHERE e.rel_type='requires' AND COALESCE(e.status,'published')='published'
  AND n.attrs::json->>'level' ~ '^[1-5]$'
GROUP BY 1 ORDER BY 1 NULLS LAST;

-- 症状 1：分类命中率按来源
SELECT CASE WHEN source_url LIKE 'llm://voced-kg/boss%' THEN 'BOSS(LLM)' ELSE '国标/其它' END src,
       count(*) FILTER (WHERE category IS NOT NULL) has_cat,
       count(*) FILTER (WHERE category IS NULL) no_cat
FROM kg_node WHERE type='skill_level' GROUP BY 1;
```

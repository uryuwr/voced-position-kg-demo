# 系统架构问题与优化 · 从「能力体系全景」视角

> 依据：
> - `知识图谱接口预研/image.png`：图谱是「树 + 网 + 链」三层混合，67% 边堆在底层技能 N:M 网、不可读；应渐进式展示。
> - `知识图谱接口预研/knowledgeGraph.json`（预研目标契约 capability）：`industry / major / position / skill`；position 带 **level**、skill 带 **category(6类)+level**；边只有 `contain`(18) + `require`(54)。
> - 当前系统：`backend/`（PostgreSQL `kg_edge/kg_node`）+ `schemas/graph_schema.yaml`。

## 一、图谱要回答的核心问题（关注点）

**行业/专业下有哪些岗位 → 岗位之间怎么晋升 → 每个岗位需要哪些技能、到什么等级。**
本质是「能力体系的**结构化全景**」，不是「关系网络的**拓扑探索**」。这句话是判断架构对错的标尺。

三层结构（image.png）：

| 层 | 语义 | 基数 | 形态 | 例 |
| --- | --- | --- | --- | --- |
| 归属树 | contain | 1:N | 树、无交叉 | 行业→专业→岗位 |
| 关联网 | require / associate | N:M | 网、可交叉 | 岗位↔技能 |
| 进阶链 | progress | 1:1 有向 | 链 | 岗位 tier 递进、技能 L1→L5 |

## 二、当前系统的错配（问题）

### P0-1 缺「晋升」维度——「岗位怎么晋升」根本回答不了
- 预研 `position` 有 **level**（岗位层级 1/2/3…），可表达「运营专员→运营主管→运营总监」的进阶链。
- 当前 `occupation` **没有 level/tier 字段，也没有岗位→岗位晋升边**（`related_to` 里也无 occ↔occ）。
- 结果：三大关注点里的「岗位之间怎么晋升」，**当前数据模型完全不支持**。

### P0-2 技能碎片化 + 无分类——底层网更乱、无法降噪
- 预研 `skill` = 一个技能节点 + `level`(1–5) 字段 + `category`（运营策略/数据能力/内容创作/商业分析/技术工程/通用素养 6 类）。
- 当前 `skill_level` 把「技能×等级」揉成**独立节点**（Python·L1、Python·L2 是两个点）→ 技能层节点/边成倍膨胀；且**无 category**。
- 结果：① image.png 说的「67% 边堆在技能 N:M 网」在当前更严重；② 无法做「高频共享技能按类别提取到侧栏」这个关键降噪手段。

### P0-3 归属树方向不统一、与关联网混淆
- 预研 `contain`：`industry→major→position`（父→子，1:N，一条语义、方向统一，清晰树）。
- 当前拆成两条不同语义边：`belongs_to`(occupation/major**→**industry，子→父) + `prepares_for`(major→occupation)，方向相反、语义混（归属 vs 培养对口）。缺「专业 contain 岗位」的树边。

### P0-4 `related_to` 2.9 万条滥用（见 `docs/边关系规则对比与整改.md`）
- 底层网爆炸的直接放大器；与 image.png「N:M 不可读」叠加。

### P1-1 接口是「通用图 BFS」，不是「能力全景聚合」
- 当前读路径：`explore(depth BFS)` / `expand(1跳)` / `by-major` / `list_nodes` —— Neo4j Browser 平替式的通用图探索。
- 前端拿到一坨 nodes+edges 自己拼、自己布局 → 极易全量渲染。
- 预研 `capability` 契约反过来：**服务端直接给结构化能力全景**（分层节点 + contain/require + level/category + child_count/order），前端只渲染。

### P1-2 前端默认「力导向全量图」——正是 image.png 批判的反例
- 我做的 Cytoscape 版默认 force 全量渲染，"把 85 条一次全画，谁都读不了"。
- 缺：默认分层树布局、技能层折叠、共享技能侧栏、焦点过滤。力导向对「树 + 链」本就是错误呈现（把有向层级打散成无向飘网）。

## 三、优化方案

### 数据 / 模型层
1. **给 occupation 加 `level`（岗位层级）**，并建**岗位晋升链**（同专业/岗位族内按 level 递进；显式 `advances_to` 边或用 level 排序隐式生成）。→ 补齐「怎么晋升」。
2. **给 skill 加 `category`（6 类）**；评估把 `skill_level` 合并节点重构为「skill 节点 + level 作边/属性」（对齐预研，显著减少技能层碎片）。这是较大重构，可先加 category、后做合并。
3. **理顺归属树**：以 `contain`(父→子 1:N) 统一表达 行业→专业→岗位；`prepares_for` 只保留「专业↔岗位对口」这层关联语义，不再兼作归属。
4. **`related_to` 语义化拆分**（P0，详见边关系整改报告）。
5. 给每条边打 **`structure_layer`= tree / net / chain** 标签，前端据此分层渲染与折叠。

### 接口层
6. 新增**能力全景聚合接口** `GET /v1/capability?industry=|major=`，直接返回：归属树(contain) + 岗位晋升(level/chain) + 岗位-技能矩阵(require，含 category 与**共享度**标记)。对齐 `knowledgeGraph.json`。前端不再自己 BFS 拼图。
7. 图接口响应给边带 `structure_layer` 与技能**共享度**（被引用次数），供前端"共享技能侧栏 + 焦点降噪"。

### 前端 / 展示层
8. **默认视图 = 分层树 + 晋升链**（行业→专业→岗位三层，dagre/层次有向布局），默认**折叠技能层（L4）**——从 85 条降到 ~28 条可读。
9. 技能层**渐进展开**：悬停岗位展开其 require 技能；焦点过滤（点行业/专业高亮其子树+关联，其余降透明）；**高频共享技能（被多岗位引用）提取到右侧栏、按 category 分组、不画线**（消除星形汇聚）。
10. 岗位晋升用**链式有向**箭头呈现（level 递进），与归属树正交摆放。
11. 力导向**降级为「关联网探索」可选项**，不再做默认。

## 四、优先级

- **P0**：① occupation 加 level + 岗位晋升链（补「怎么晋升」）；② skill 加 category；③ related_to 语义化 + 归属树理顺。—— 数据模型是地基，不先补，前端怎么改都读不出「晋升/能力全景」。
- **P1**：能力全景聚合接口 `/v1/capability`；前端默认改分层树 + 技能层折叠 + 共享技能侧栏。
- **P2**：skill_level → skill+level 合并重构；关联网力导向作为高级探索可选。

## 五、一句话

当前是「**通用图数据库探索器**」的架构（力导向 + BFS 探索），而业务要的是「**能力体系结构化全景**」产品（分层树 + 晋升链 + 按需展开的技能矩阵）。范式错配的根因在**数据模型缺 level/tier(晋升) 与 category(技能分类)**、边语义混乱、以及**没有面向全景的聚合接口与分层渲染前端**。先补模型，再补聚合接口，最后前端从"全量力导向"改为"分层树 + 渐进展开"。

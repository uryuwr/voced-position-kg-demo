# 前端「知识图谱接口预研」vs 当前服务端 · 差异分析

> 对照材料：`知识图谱接口预研/`（`knowledge-graph-api.md` / `knowledgeGraph.ts` / `knowledgeGraph.json`）  
> 对照实现：`schemas/graph_schema.yaml`、`kg_node`/`kg_edge`/`kg_skill_prereq`、`/v1/search|graph/*|kg/nodes|node`  
> 日期：2026-08-07

**结论摘要**：**语义上四维图可表达，库结构大体支持；接口契约与预研差别大，不能直接对上前端 TS/mock。** 需一层适配 API 或前端改调现网。

---

## 1. 数据库存储结构是否支持？

### 1.1 四层节点

| 预研 `type` | 当前库 `kg_node.type` | 支持度 |
| --- | --- | --- |
| `industry` | `industry` | ✅ 一致 |
| `major` | `major` | ✅ 一致 |
| `position` | **`occupation`** | ⚠️ 语义同岗位，**命名不同** |
| `skill` | **`skill_level`**（按 L1–L5 分节点，逻辑技能用 `skill_key` 聚合） | ⚠️ **粒度更细**；预研 mock 是扁平 skill |

另有 `course` / `credential`，预研 Tab1 不用，库里有。

### 1.2 层间边（含多对多）

| 预研边 `type` | 方向（预研） | 当前 `rel_type` | 方向（库） | 支持度 |
| --- | --- | --- | --- | --- |
| `contain` 行业→专业 | industry → major | `belongs_to` | **major → industry** | ⚠️ **有边、方向相反**；适配时翻转或统一 |
| `contain` 专业→岗位 | major → position | `prepares_for` | major → occupation | ✅ 同向（类型名不同） |
| `require` 岗位→技能 | position → skill | `requires` | occupation → skill_level | ✅ 同向；目标是 skill_level |
| `prerequisite` 技能→技能 | skill → skill | **`kg_skill_prereq` 表**（非 `kg_edge`） | skill_key → skill_key | ⚠️ **数据在**；不在通用边表，需 join/投影 |
| `related` | 弱关联 | `related_to` 等 | 有 | ✅ 预留可用 |

**多父 / 多对多**：库是边表，岗位可挂多专业、技能可被多岗位 require → **支持**。  
**孤立行业**：行业节点独立存在，无专业边也可查询 → **支持**（注意：若只 join 边会漏，需节点集独立取）。

### 1.3 预研节点字段 vs 库字段

| 预研字段 | 库/现状 | 支持度 |
| --- | --- | --- |
| `id` 全局稳定 | ✅ `kg_node.id` 如 `CN:industry:BOSS_ZHIPIN:…` | ✅ 已是全局 id |
| `biz_id` number 业务主键 | ❌ 无数字自增主键；id 为字符串复合键 | ❌ **模型不匹配**（可派生 hash/不映射） |
| `type` | ✅ 有，取值集合不同（见上） | ⚠️ 需映射 |
| `name` / `description` | ✅ | ✅ |
| `code` | 部分在 `attrs`（如 major code） | ⚠️ 非一等列，可投影 |
| `category` 技能分类 | ❌ **无**运营策略/数据能力等分类字典 | ❌ 需补数据或前端本地分类 |
| `status` published/draft/offline | published/draft/**disabled**/archived | ⚠️ `offline`↔`disabled` 映射 |
| `level` | skill 在 `attrs.level_int` / 节点名；岗位职级弱 | ⚠️ 部分有 |
| `weight`（节点大小） | 权重多在 **边上** `kg_edge.weight` | ⚠️ 节点 weight 非标配 |
| `child_count` | ✅ `kg_node.child_count`（向下：业→专→岗→技能） | ✅ 已补列+回填 |
| `order` | ✅ `kg_node.sort_order` → API `order` | ✅ 已补列+回填 |
| `updated_at` ms | 有更新人字段；时间戳形态需确认 | ⚠️ 可补投影 |

### 1.4 量级（当前 CN，约）

| 层 | 量级级 | 对预研「全量 full」影响 |
| --- | ---: | --- |
| industry | ~150 | 可全量 |
| major | ~2k | 偏大 |
| occupation | ~1.6k | 偏大 |
| skill_level 节点 | ~9k+ | **过大**；若聚合成 skill_key 仍千级 |
| edges | ~5 万 | **不宜一期无分页 full 整图** |

→ 结构上能表达四层图；**全量快照一期直接吐全库不现实**，需截断 / 按行业 scope / 懒加载（与预研 B 节一致）。

### 1.5 存储结论

| 诉求 | 结论 |
| --- | --- |
| 四维关联图 | **支持**（命名与边方向需适配） |
| 多对多、孤立节点 | **支持** |
| 技能前置 | **支持**（表 `kg_skill_prereq`） |
| 技能分类配色 | **当前不支持**（缺分类数据） |
| `biz_id` 数字主键 | **不支持**（全局字符串 id 体系） |
| 预研 mock 体量的「整图一次下发」 | 结构可做；**全库数据量不适合无过滤 full** |

## 2. 已实现接口 vs 预研契约

### 2.1 接口清单对照

| 预研接口 | 用途 | 当前实现 | 一致？ |
| --- | --- | --- | --- |
| `GET …/knowledge_graph/actions/full` | 全量 nodes+edges+stats+categories+version | **无** | ❌ |
| `GET …/knowledge_graph/nodes?type=` | 分层列表 | `GET /v1/kg/nodes?type=&page=` | ⚠️ 路径/分页参数不同（`page` vs `$offset`） |
| `GET …/nodes/{id}/neighbors` | 懒加载展开 | `POST /v1/graph/expand` | ⚠️ **有能力**；方法/路径/字段不同 |
| `GET …/actions/search?keyword=` + **path 祖先链** | 顶栏搜索定位 | `GET /v1/search?q=` 仅种子 | ⚠️ 有搜索 **无 path** |
| `GET …/nodes/{id}` 详情 parents/children/related_skills | 详情面板 | `GET /v1/node?id=` 单节点；邻居另 expand | ⚠️ 未打包成详情 DTO |
| — | 兼容 BFS 探索 | `GET /v1/graph/explore` | 预研未定义（我们额外有） |

### 2.2 响应形态（最关键）

预研核心：

```text
{ version, truncated, stats, categories, nodes[], edges[] }
边：{ id, source, target, type, weight?, required_level? }
节点：{ id, biz_id, type: industry|major|position|skill, … }
```

当前 expand/explore 大致：

```text
{ roots?, nodes[], edges[], paths?, meta }
边：{ id, src_id, dst_id, rel_type, weight, … }   // 非 source/target/type
节点：{ id, type: industry|major|occupation|skill_level, name, status, … }  // 无 biz_id
```

| 维度 | 预研 | 当前 | 差异 |
| --- | --- | --- | --- |
| 扁平 nodes+edges | 要求 | explore/expand **已是扁平** | ✅ 形态同构方向一致 |
| 嵌套树 | 禁止 | 未用树 | ✅ |
| 边字段名 | source/target/type | src_id/dst_id/rel_type | ❌ 命名 |
| 边类型枚举 | contain/require/prerequisite | belongs_to/prepares_for/requires + 表 prereq | ❌ 需映射表 |
| 节点 type 枚举 | position/skill | occupation/skill_level | ❌ 需映射 |
| skill 粒度 | 一个 skill 一节点 | 多 skill_level，或 bundle 聚合读 | ⚠️ 产品需约定图上显示哪一层 |
| version / truncated / stats / categories | full 必带 | 无（meta 字段另一套） | ❌ |
| search 带 path | 必带 | 无 | ❌ |
| child_count | 懒加载必需 | 列表可 `include_counts`，非预研字段名 | ⚠️ |
| 管理端 status 过滤 | full 的 status 参数 | list `scope=manage` + status；图读路径默认 **仅 published** | ⚠️ 管理看草稿要 scope |

### 2.3 能力等价（不改前端命名时的映射建议）

```
预研 contain(行业→专业)  ⇐  翻转 belongs_to(专业→行业)
预研 contain(专业→岗位)  ⇐  prepares_for
预研 require(岗位→技能)  ⇐  requires（目标 skill_level 或再聚 skill_key）
预研 prerequisite         ⇐  kg_skill_prereq 投影成边
预研 neighbors            ⇐  POST /v1/graph/expand
预研 search 无 path        ⇐  GET /v1/search（缺祖先链需新算）
预研 full                 ⇐  无；可新建适配层按行业/截断组装
```

### 2.4 接口结论

| 项 | 判断 |
| --- | --- |
| 是否「已有 search + 1 跳 expand」业界图探索 | **有**，与预研懒加载 **能力接近** |
| 是否与预研路径/DTO/枚举一致 | **不一致**（差一版适配层） |
| 一期 full 契约 | **未实现** |
| 搜索 path、categories、version | **未实现** |
| 前端 mock 能否当现网响应 | **不能直接用** |

## 3. 差异量级总览

| 类别 | 差距 |
| --- | --- |
| **库能否支撑页面** | **中小**：能画四层图；差分类字典、biz_id、边方向约定、skill 展示粒度 |
| **接口契约一致** | **大**：路径、方法、字段名、枚举、full/path/categories 均未对齐 |
| **推荐落地** | **B 路径优先**（对齐现网 search+expand + 适配器）或 **A 新增 `/v1/knowledge_graph/*` 适配层** 投影预研 DTO，不必改 PG 主模型 |

### 建议（给评审）

1. **id**：继续用现网全局字符串 id，放弃数字 `biz_id`（或 `biz_id` 改 string 可选）。  
2. **type 映射表**写死在适配层：`occupation↔position`，`skill_level|skill_key↔skill`。  
3. **边**：对外统一 `contain/require/prerequisite`，对内读写现 rel。  
4. **一期不做全库 full**：`full?industry_id=` 或 `truncated`+上限；默认推荐 search+expand。  
5. **Tab2 技能前置**：读 `kg_skill_prereq`；环检测已有 BR-05。  
6. **分类**：产品定 6 类规则（规则/人工）再进 attrs 或字典表。

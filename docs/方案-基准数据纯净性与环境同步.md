# 方案：基准数据的纯净性与环境同步

2026-08-20。目标：本地维护一份可信的**图谱基准数据**，不被联调点击、单测、E2E 污染，
并能用脚本同步到预生产 / 生产。

## 一、先看问题出在哪

不是「防污染没做好」，而是**基准数据从来没有被定义过**。它现在等于「本地
`voced_kg` 库的当前状态」，而这个库同时扮演三个角色：

| 角色 | 谁在写 | 写什么 |
|---|---|---|
| 采集落库目标 | `migrate` + 各修正脚本 | 图数据 |
| 联调库 | 人点页面、管理台建数 | 图数据 + 业务数据 |
| 测试库 | `e2e_robustness`、`e2e_skill_level`、各种 `--dry-run` 之外的验证 | 临时 fixture |

三个角色挤一个库，污染是必然的。实测残留（2026-08-20）：

```
__e2e_skill_*        8 个 skill_level
测试技能*             5 个 skill_level
临时测试岗位Y          1 个 occupation
MANUAL 来源节点        78 个（含人工建数与测试遗留，无法区分）
```

**已经扩散到真实数据上**：

```
混凝土工        -requires->  __e2e_skill_102413 · L2
临时测试岗位Y    -requires->  __e2e_skill_103525 · L1 / L2
```

后果不是"多几条垃圾"这么轻。`scripts/fix_duplicate_requires.py` 那次修重复边，
把「混凝土工 / `__e2e_skill_102225`」当成真实重复处理并归档了一条边 ——
**测试数据参与了业务规则的判定**。同理，它们也计入了覆盖率统计（「821 个岗位技能
覆盖 100%」里就含「临时测试岗位Y」）。

`biz_*` 16 张表全是本地联调产物（诊断 60 场、答题 119 条、`biz_user_skill` 153 行）。
这些**不该**进基准，各环境自己长。

## 二、基准数据的定义

基准 = **图谱内容**，不含任何运行时痕迹。

进：
- `kg_node` / `kg_edge`：**只要线上行（`is_draft = false`）**
- `kg_skill_category`（分类字典）
- `kg_skill_prereq`（技能先修）

不进：
- 全部 `biz_*` —— 用户运行时数据，各环境独立
- `kg_proposal` —— 审核队列，环境相关
- 草稿行（`is_draft = true`）—— 那是某个人编辑到一半的中间态，不是内容
- 任何 fixture

**载体是版本化的导出文件，不是"某个库的当前状态"。** 这条最重要：
只要基准的定义还是「去 voced_kg 看一眼」，它就永远会被下一次联调改掉。

## 三、三库隔离

```
voced_kg          基准库    只由 migrate 与修正脚本写；8090 只读看它
voced_kg_dev      联调库    8088 连这里：页面点击、管理台建数、跑测试，随便脏
voced_kg_test     测试库    （待做）每次跑测试前 drop-create
```

**2026-08-20 已落地前两个**。踩了一次：清洗完基准库后才发现 8088 与 8090 连的
是**同一个库** `voced_kg`，只是账号一个可写（`voced`）一个只读（`voced_kg_ro`）——
只读端口是达到了，但联调仍在往基准库写，清干净的数据马上会被污染回去。

现在 `voced_kg_dev` 由 `CREATE DATABASE ... WITH TEMPLATE voced_kg` 整库复制而来
（要求源库当时没有其它连接，所以先停了三个实例），`DATABASE_URL` 在 `backend/.env`
里显式指向它。

⚠ `settings.py` 里 `DATABASE_URL` 的默认值仍是 `voced_kg` —— 那是兜底，不是配置
真源。`.env` 里没配这一行时会**静默连上基准库**，这就是之前两个端口撞在一起的原因。
新环境部署时先确认 `.env` 有这行。

隔离已实测：往 `voced_kg_dev` 插一条 `CN:manual:industry:__isolation_probe`，
`voced_kg` 查得到 0 条。

落地成本很低，因为 `tests/_e2e_server.py` 已有「dotenv 加载完成后改内存值」的机制
（`settings.AUTH_BYPASS = True` 那套）。加一行改 `DATABASE_URL` 即可，不动 `.env`：

```python
# tests/_e2e_server.py —— 测试实例强制连测试库，避免写坏基准
settings.DATABASE_URL = os.getenv("TEST_DATABASE_URL", settings.DATABASE_URL.replace("/voced_kg", "/voced_kg_test"))
```

⚠ 别指望「测试里小心点就不会写基准库」。`e2e_robustness.py` 的 C2 用例本身就是
**写入测试**（验证非法 `attrs.level` 被拒 400），它必须写库。靠自觉挡不住。

## 四、fixture 规范

现在的测试数据有四五种命名（`__e2e_`、`__test`、`__cat_e2e_`、「临时测试」、「测试技能」），
没法统一识别，也就没法统一清理。定一条：

- id 前缀 `TESTFX:`，且 `attrs.test_fixture = true`（双标记：id 便于 LIKE 扫，
  attrs 便于导出时排除）
- 测试用 `try/finally` 自己清；清理失败不算测试失败，但要打日志
- 闸门 `scripts/verify_no_test_fixtures.py`：扫到任何 fixture 就 exit 1，
  **挂在导出脚本入口**，不让带 fixture 的快照被导出

为什么要双标记：id 前缀能被 `LIKE 'TESTFX:%'` 秒扫，但历史数据改不了 id；
`attrs.test_fixture` 可以给存量补标记。

## 五、导出 / 导入

### `scripts/export_baseline.py`

产出两个文件到 `data/baseline/`：

```
kg_baseline_<yyyymmdd>.jsonl.gz     每行一条节点或边
kg_baseline_<yyyymmdd>.manifest.json 行数、sha256、导出时各段覆盖率
```

要点：
- **只导 `is_draft = false`**。漏掉这个谓词，别人编辑到一半的草稿会被当成基准
  发到生产（新主键是 `(id, is_draft)`，同一 id 有两行，`WHERE id = ...` 会取到两条）
- 排除 fixture（`attrs.test_fixture` 与 id 前缀双重过滤）
- manifest 里存**覆盖率快照**（岗位数、各段覆盖比例、分类分布），导入后比对，
  数字不对就是导错了 —— 这比只校验行数有用：行数对而内容错的情况真发生过
  （`attrs = EXCLUDED.attrs` 把归一化结果盖回旧形态，行数一模一样）
- jsonl 而非 pg_dump：pg_dump 带 schema 与 owner，跨环境不通用；jsonl 可读、
  可 diff、可进 git（gz 后约几 MB）

### `scripts/import_baseline.py`

```bash
python -X utf8 scripts/import_baseline.py --file data/baseline/kg_baseline_20260820.jsonl.gz --dry-run
python -X utf8 scripts/import_baseline.py --file ... --apply
```

要点：
- **幂等 upsert，绝不 TRUNCATE**。预生产库与 `bcs-ai-agent` 共用，清表会打死别人
- `ON CONFLICT (id, is_draft) DO UPDATE` —— 2026-08-19 主键改了，写 `(id)` 直接报
  `no unique or exclusion constraint matching`
- 写入显式带 `is_draft = false`
- `--dry-run` 输出 diff：新增 / 更新 / 目标环境有而基准没有（后者**不删**，
  只报告 —— 那可能是目标环境自己的数据）
- 导入后自动跑闸门，任一不过就非零退出：

```
scripts/verify_backfill.py after         技能档位刻度方向
scripts/fix_duplicate_requires.py --dry-run   一岗一技能一档
scripts/verify_draft_leak.py             草稿没泄漏到前台
scripts/check_orphan_edges.py            边两端都存在（外键已删，只能靠它）
scripts/verify_skill_key.py              skill_key 形态
```

## 六、同步流程

```
本地基准库 voced_kg
   │  export_baseline.py（自带 fixture 闸门）
   ▼
data/baseline/kg_baseline_<ver>.jsonl.gz  ← 进 git，可回溯、可 diff
   │  import_baseline.py --dry-run   看 diff，人工确认
   ▼
预生产（共用库，只 upsert）→ 跑闸门 → 联调验证
   │  同一个文件，不重新导出
   ▼
生产 → 跑闸门
```

两条纪律：

1. **预生产与生产用同一个快照文件**，不各导一次。重新导出就意味着两个环境的数据
   不是同一份，联调过的东西不等于上线的东西。
2. 导入记录写进 `kg_baseline_history`（版本、sha256、时间、执行人、闸门结果），
   出问题能定位是哪一版带进去的。

## 七、落地顺序

| 步骤 | 做什么 | 阻塞发布？ |
|---|---|---|
| 0 | 清掉现有 14 个 fixture 节点及其边 | 是 |
| 1 | 建 `voced_kg_test`，测试改连它 | 是 |
| 2 | `export_baseline.py` + fixture 闸门 | 是 |
| 3 | `import_baseline.py`（dry-run + apply + 闸门链） | 是 |
| 4 | 建 `voced_kg_dev`，联调改连它 | 否，可后补 |
| 5 | fixture 规范落到各测试脚本 | 否，防复发 |

第 0–3 步是「能把干净数据发上去」的最小闭环。第 4 步之前，基准库仍会被联调污染，
但有了闸门与 diff，至少污染进不了快照。

## 八、一个容易忽略的点

`data/graph/kg.sqlite`（采集库）**不是基准数据**，也不能替代快照。因为大量修正只发生在 PG：
`attrs.level` 回填 546 个、`category` 列同步 12642 个、课程归档 1487 个、
重复边清理。这些改动 SQLite 里没有或形态不同 —— 谁拿 SQLite 重灌一次，数字就
逐位退回（2026-08-18 已经发生过一次，全程零报错）。

所以 SQLite 是**采集中间产物**，PG 基准库是**内容真源**，导出的快照是**交付物**。
三者不能互相替代。

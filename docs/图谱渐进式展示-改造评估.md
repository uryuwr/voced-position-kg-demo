# 图谱「渐进式信息展示」改造评估

对照策划的四条策略，评估前后端改造量。

> **实施状态（已完成）**：下述五步已全部落地并验证，服务已重启生效。
> 唯一未达成的是**晋升链的数据**——实施过程中查库确认，当前岗位全部来自「人社部职业分类大典」，
> 1329 个岗位中 1301 个（97.9%）`level` 相同、仅 17 个名称含层级词，
> 该数据源**根本不含职级维度**。因此晋升链的接口、派生逻辑、前端渲染已全部就位并跑通
> （物流设施运行与维护等少数专业能派生出 3 条），但绝大多数专业返回空数组，
> 需等企业职级表 / 招聘级别爬取数据接入后自动生效，届时无需改代码。

**结论**：四条策略里三条是纯前端改造（现有代码已有 60% 基础，可复用）；唯一的硬阻塞是**晋升链 `advances_to` 在整个 backend 里零实现、零数据**——而它恰恰是策划核心原则里「怎么晋升」那一半答案。

## 一、策略 vs 现状对照

| 策划策略 | 现状 | 差距 | 改造侧 |
| --- | --- | --- | --- |
| **默认折叠 L4**（只展示行业→专业→岗位三层 + 晋升链） | `/v1/capability` 一次性返回全部岗位的全部技能明细（`skill_total` 可达数百）；前端 `applyDimFilter` 按**节点类型**做纯前端显隐 | 后端仍全量吐技能（正是「85 条边一次画完」的来源）；前端默认勾选包含 `skill_level` | 前 + 后 |
| **悬停展开**（hover 岗位 → 展开其技能边） | `cy.on("mouseover")` 只弹 tooltip，不加载/不展开边 | 需新增 hover 懒加载 + 临时边渲染 | **纯前端** |

| **共享技能侧栏**（S17/S10 等高频技能提到侧栏，不画线） | `aggregateSkillNodes` 已按 `skill_key` 聚合技能节点 | 聚合结果只统计了「等级数」(`counts.level`)，**没有统计「被几个岗位引用」**——而引用数正是判定「高频共享」的依据 | 前 + 后 |

## 二、后端改造

### 1. `/v1/capability` 增加渐进式参数（改造主体）

现有签名见 [main.py:768](../backend/api/main.py#L768)。新增三个参数：

| 参数 | 类型 | 默认 | 说明 |
| --- | --- | --- | --- |
| `include_skills` | bool | **`false`** | 默认不返回技能明细，只在每个岗位上给 `skill_count`。置 `true` 恢复现有全量行为（兼容旧调用） |
| `include_progression` | bool | `true` | 是否返回岗位间晋升链 `progressions[]` |
| `shared_skill_min_occ` | int | `2` | 被 ≥N 个岗位共同要求的技能，收进 `shared_skills[]` 供侧栏渲染；`0`=不计算 |

响应体新增两个顶层字段（`root`/`industries`/`occupations`/`meta` 不变）：

```jsonc
{
  "progressions": [                      // 晋升链，对应策划 E6
    { "from": "CN:occupation:...:初级", "to": "CN:occupation:...:中级",
      "from_level": 1, "to_level": 2, "confidence": "derived" }
  ],
  "shared_skills": [                     // 共享技能侧栏，不参与画线
    { "skill_key": "Python", "occ_count": 7,
      "levels": ["L2","L3"], "occupation_ids": ["...", "..."] }
  ]
}
```

`occupations[].skills` 在 `include_skills=false` 时为 `[]`，同时 `occupations[].skill_count` 给出真实数量（供节点上显示「技能 12 ▸」角标）。

> 注意：默认值从「全给」翻转为「不给」是**破坏性变更**。现有 `frontend/capability.html` 与 admin-console 内嵌的 `renderCapability` 都直接读 `o.skills`，改造时必须同步，否则技能列表静默变空。

### 2. hover 懒加载 —— **零改造**

已有 [`GET /v1/occupations/skills`](../backend/api/main.py#L488)，`occupation_id` + `aggregate=true` 直接可用，返回按 `skill_key` 聚合的 bundle（含 levels / required_level）。前端 hover 直接调它即可，不需要新接口。

### 3. `advances_to` 落地（阻塞项，见第四节）

`query.py` / 写入 / 迁移脚本中 `advances_to` **零命中**，仅 [graph_schema.yaml:92](../schemas/graph_schema.yaml#L92) 有本体定义。需要新增派生逻辑与查询。

## 三、前端改造（`frontend/admin-cytoscape.html`）

1. **默认维度去掉技能**：`DIMS` 默认勾选改为 `industry/major/occupation`。`applyDimFilter` 逻辑本身不用动——它已经是「纯显隐、不重查后端」，正好符合渐进式语义。

2. **hover 展开技能**：在 [`cy.on("mouseover", "node")`](../frontend/admin-cytoscape.html#L771) 里，当 `type==="occupation"` 时防抖 ~250ms 调 `/v1/occupations/skills`，结果以**临时元素**加入（打 `.ephemeral` class），`mouseout` 时整批移除。要点：结果按 `occ_id` 缓存避免重复请求；技能节点复用 `aggregateSkillNodes` 的 bundle 形态，一个技能一个节点而非一等级一节点（否则边数反而涨）。

3. **焦点过滤改语义**：`pinGraphFocus` 里把固定 2 跳
   ```js
   for (let h = 0; h < hops; h++) keep = keep.closedNeighborhood();
   ```
   改为按边类型分层遍历——沿 `contain`/`parent_of`/`belongs_to`/`prepares_for`（tree 层）做**无限深度**下钻取子树，再并上子树节点的 net 层关联边。`.dim` 样式已达标，不用改 CSS。

4. **共享技能侧栏**：新增右侧可折叠面板，渲染 `shared_skills[]`，按 `occ_count` 倒序；点某项时高亮引用它的岗位节点（用 `occupation_ids`），**但不建边**——这正是消除星形汇聚的关键。

5. **补关系中文名**：[`REL_ZH`](../frontend/admin-cytoscape.html#L449) 缺 `advances_to`（晋升）、`belongs_to`（归属行业）、`offers_course`（开设课程）、`contain`、`skill_progress`，晋升链画出来会显示英文原文。

## 四、阻塞项：晋升链没有数据

策划表写「E6 晋升链（28 条边）」，但当前一条都没有。两个选择：

**A. 过渡方案（可立即做）**——由 `occupation.level` 派生。同一专业下的岗位按 `level` 排序，相邻层级间连 `advances_to`，标 `confidence=derived`。
风险：`occupation.level` 目前是**正则 mock 出来的 1/2/3**（按岗位名里的「初级/中级/高级」等词猜的），派生链的质量完全取决于这批 mock。同一层级有多个岗位时会产生 N×M 交叉边，需要按岗位族（`skill_key` 或名称主干）分组后再连，否则边数会爆而不是收敛到 28。

**B. 等真实数据**——依赖爬取的企业职级表 / 招聘级别数据（爬虫线任务，且有需登录站点已挂 HITL 待办）。

建议先上 A 打通前后端链路和渲染，数据置信度标 `derived`，B 到位后直接替换边、前端不用改。

## 五、执行顺序

1. 后端 `/v1/capability` 加 `include_skills` / `shared_skill_min_occ`（含 `shared_skills` 聚合），同步改 `capability.html` 与 admin-console 的 `renderCapability` —— 默认折叠 L4 即刻生效
2. 前端 hover 懒加载 + 默认维度调整 —— 复用已有接口，无后端依赖，可与 1 并行
3. 前端焦点过滤改子树语义 + 补 `REL_ZH` —— 纯前端
4. `advances_to` 派生（方案 A）+ `/v1/capability` 返回 `progressions[]` + 前端画晋升链
5. 共享技能侧栏

1–3 之后策划表里「28 条边、完全可读」的观感目标基本达成；4 补上「怎么晋升」；5 是消除星形汇聚的收尾。

## 六、实施结果与验证

改动文件：`backend/kg/pg_store/query.py`、`backend/api/main.py`、
`frontend/admin-cytoscape.html`、`frontend/admin-console.html`、`frontend/capability.html`。

顺带修掉的既有 500：`capability_by_major` 里用了未导入的 `session()`（全文件其余均为 `connect()`），
以及缺 `::text` 转换的判空参数；同时补上原本算了不用的 `region` 过滤、
把写死的 `status='published'` 统一为 `_PUBLISHED_SQL`（否则漏掉 status 为 NULL 的节点）。

验证记录（`物流设施运行与维护`，53 岗位 / 715 技能）：

| 场景 | 结果 |
| --- | --- |
| 默认（折叠） | `skills_included=false`，技能明细为空、`skill_count` 正常，共享技能 10 项、晋升链 3 条 |
| `include_skills=true` | 技能明细回全，`skill_total` 一致 |
| `shared_skill_min_occ=0&include_progression=false` | 两项聚合均为 0，省一次技能明细扫描 |
| 专业不存在 / 缺参 | 404 / 400 |
| 未登录直连 `/v1/capability` | 401 `missing_authorization`（鉴权正常，须走 `/admin` 内 UC 登录态） |

共享技能实测 TOP：`培训指导 ×7`、`培训与指导 ×5`——正是策划说的 S17/S10 那类高频汇聚点。
顺带暴露一个数据质量问题：「培训指导」与「培训与指导」被算作两个不同技能，
技能名归一化未做，建议后续在爬取/清洗侧统一，本次未处理。

三个页面的内联脚本均通过 `node --check`；服务重启后 `/openapi.json` 已含三个新参数。

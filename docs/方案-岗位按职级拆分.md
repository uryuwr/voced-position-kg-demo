# 方案：岗位按职级拆分

> 2026-08-18 · 根因见 [根因分析-国标采集丢失的两个维度](根因分析-国标采集丢失的两个维度.md)
> 解决的是那份文档里的症状 3、4：国标岗位技能要求一律顶格 L5，岗位职级 97.5% 都是 `2`。

## 0. 结论先行

- **拆几档由数据自己决定，不按国标等级数、也不按招聘热度。** 判据是「相邻档位的技能要求形态是否真的不同」——实测 1666 对相邻档位里有 **735 对技能集合完全相同**，无脑按国标等级拆会造出一半重复节点。
- 拆分素材**已经在库里**（6611 条 `archived` 的 `requires` 边），不需要新采集。
- **迁移窗口就是现在**：业务表对岗位的引用总计不到 80 行，全是测试数据。
- 招聘网站拿不到职级热度这条路**已经论证过走不通**，不要重走（见第 9 节）。

## 1. 拆分规则：按「技能要求形态」拆

### 1.1 实测依据

对 483 个有多档素材的国标岗位，把每档的 `(技能集合, 权重分布)` 作为签名，统计签名的去重种类数：

| 档位数 / 实际不同的签名种类 | 岗位数 | 该拆几个 |
|-|-|-|
| 5 档 / **5 种** | 35 | 5 |
| 5 档 / 4 种 | 77 | 4 |
| 5 档 / 3 种 | 68 | 3 |
| 5 档 / 2 种 | 87 | **2** |
| 5 档 / **1 种** | 16 | **不拆**（见第 2 节） |
| 4 档 / 4 种 | 18 | 4 |
| 4 档 / 3 种 | 45 | 3 |
| 4 档 / 2 种 | 65 | 2 |
| 4 档 / 1 种 | 2 | 不拆 |
| 3 档 / 3 种 | 29 | 3 |

**只有 35 个岗位真正需要 5 档。** 87 个岗位虽然国标给了 5 级，但要求只有 2 种形态——按等级数硬拆会有 3 个节点是重复副本。

按签名拆的总量约 **1100 个节点**；无脑按等级数拆是 2145 个。少掉的一半全是重复。

### 1.2 算法

```
对每个国标岗位 O：
  1. 按 attrs.level 分组，取每档的签名 sig(lv) = (sorted(skill_keys), sorted(weights))
  2. 沿 lv 升序扫描，签名相同的**连续**档位合并成一个区间
     —— 只合并相邻档，不合并跨档的相同签名（L1、L3 相同但 L2 不同时，不能把 L1+L3 并成一个）
  3. 得到 N 个区间 → 拆 N 个职级节点，每个节点承接该区间内**最高档**的 requires 边
  4. N == 1 → 不拆，见第 2 节
```

第 2 步「只合并相邻」是关键：职级是有序的，跨档合并会造出不连续的职级区间，`advances_to` 就串不起来。

第 3 步取区间内最高档：区间内各档要求本就相同（这是合并的前提），取最高档是为了让 `attrs.level` 与 `level_range` 的上界一致。

## 2. 那 18 个「各档要求完全相同」的岗位

16 个 5 档 + 2 个 4 档，签名只有 1 种。它们**不拆**，但必须改要求档位——现在是顶格 L5（去重兜底的产物）。

**定为最低档。** 国标在最低等级就要求了这些技能，说明它们是该职业的**基础要求**；拿 L5 当基准会让匹配度虚低，这正是当前 `level=1` 岗位要求档均值 4.50 的来源。

## 3. 命名与 attrs 约定

```
name                     室内装饰设计师（初级）
level                    2                      -- 产品档，取区间上界；排序/筛选用
attrs.level_range        [1, 2]                 -- 该节点覆盖的产品档区间
attrs.level_zh           "五级/初级工、四级/中级工"  -- 国标原始等级名，可追溯
attrs.parent_occupation  CN:occupation:MOHRSS_CN:4-08-08-07
attrs.split_basis        "skill_requirement_signature"   -- 拆分依据，便于审计
confidence               official               -- 等级划分来自国标正文，非派生
```

三点约束：

**`name` 带职级不会撞现有命名。** 现有 1639 个国标岗位只有 3 个名字带职级词（助理/主任），BOSS 821 个里 20 个。

**`level_zh` 不能硬编码成一套。** 技能人员是「五级/初级工 … 一级/高级技师」，技术人员是「员级/助理级/中级/副高级/正高级」，两套并存，按原始标准取。

**中文职级名（初级/中级/高级）是展示层的，需要字典。** 当前 `level_label` 是现场拼的 `f"L{level}"`（`goal_overview.py:332`），没有名称映射也没有字典表——这一点与技能档位形成对比：技能档位有 `skill_level_meta.py` + `GET /v1/student/meta/skill-levels`，且 CLAUDE.md 明令禁止硬编码档位名。**岗位职级应比照建一份**，否则拆完仍然只能显示「L2」。

## 4. 图结构

原节点**保留为岗位族父节点**，不带 `requires` 边：

```
室内装饰设计师（族）                        ← 原节点，保留 id 不变
  ├─parent_of→ 室内装饰设计师（初级） level=2  ← 承接 L1–L2 区间的 requires 边
  ├─parent_of→ 室内装饰设计师（中级） level=3
  └─parent_of→ 室内装饰设计师（高级） level=5
                    ↑
              advances_to 依 level 升序串联
```

**原 id 不变**是迁移的关键（见第 6 节）：业务表里已有的引用继续指向族节点，不会悬空。

族节点保留 `belongs_to`（行业）与 `prepares_for`（专业→岗位）边；`requires` 边全部下移到职级节点。**族节点不再有技能构成**——这一点要在读路径上处理，否则打开族节点的技能构成页会是空的（见第 7 节）。

`advances_to` 顺带被修复：现有 137 条、覆盖 1331 个岗位里的 13 个（1%），根因是**没有可连接的对象**。拆完后同族内按 `level` 升序自动串联，能新增约 600 条有真实依据的晋升边。

## 5. 边的重建步骤

```
① 前置校验：scripts/verify_backfill.py after
   确认国标刻度方向没反——国标一级(高级技师,最高) → 产品档 5。
   CLAUDE.md 警告过：方向反了不报错、不崩，只把高级技师判成入门。
   拆分要按档位分配要求，方向错了会把「初级岗位」配上专家级要求，且全程无告警。

② 建职级节点（make_node_id，不手拼）+ parent_of 边

③ 恢复并改指 requires 边
   现在：低档边 status='archived'，最高档 published，全部挂在原节点
   目标：每条边的 src_id 改为对应职级节点，status 恢复 published
   注意 edge id 是 (src, rel, dst) 派生的 —— src 变了 id 就变了，
   是「建新边 + 归档旧边」而不是 UPDATE（与 fix_duplicate_requires 用 archived
   而非物理删除的做法一致，留审计痕迹）

④ 建 advances_to：同族内按 level 升序，相邻两档连一条

⑤ 权重校验：每个职级节点的 requires 权重 Σ≈1
   国标各档权重本就各自归一（实测方案设计 L1=25/L2=25/L3=30/L4=25/L5=20），
   拆开后天然成立；合并区间时取的是单一档位的权重集合，不做求和，所以不会破坏归一

⑥ 后置校验：verify_backfill.py after + fix_duplicate_requires.py --dry-run
   后者是回归闸门（发现重复返回非零退出码）。拆分后同一职级节点下
   不应再有同技能多档
```

**不要改 `fix_duplicate_requires.py` 的三条规则。** 它对付重跑残留是正确的，问题一直是「别把国标多等级数据喂给它」——本方案在建边阶段就按职级分流，正是从源头解决。

## 6. 迁移

```
biz_user_goal            14 行，8 个岗位
biz_diagnosis_session    57 行，19 个岗位
biz_user_learning_plan    9 行，8 个岗位
```

全是测试数据，且**族节点 id 不变**，所以这些引用不需要动——它们会指向族节点。

但要明确产品语义：**学员锁定目标时该锁族还是锁具体职级？**

- 锁**族**：语义是「我要做室内装饰设计师」，但匹配度算不出来（族节点没有 requires 边）
- 锁**具体职级**：语义是「我要做高级室内装饰设计师」，可算匹配度，且晋升路径天然可用

建议锁具体职级，族节点只作为浏览/归组的中间层。那么现有 8 个已锁定目标需要迁移到某一档——**没有正确答案**（学员当初锁的是无职级的岗位）。当前只有 14 行测试数据，随便挑一档或清空都行；等真实学员进来这就成了无解问题。**这是「现在动手」的最强理由。**

## 7. 读路径的连带改动

拆分后族节点没有技能构成，以下位置需要处理：

| 位置 | 影响 |
|-|-|
| `skill_composition.get_composition` | 打开族节点时 `items` 为空、`weight_sum=0`；应提示「请选择具体职级」或自动跳到默认档 |
| `node_detail._occupation_detail` | 同上；`skills[]` 空 |
| `goal_overview` | 「当前活跃目标」卡片的匹配度依赖 requires；锁族则算不出 |
| `learningplan/builder` | 编排依赖 `position_skills`，族节点取不到技能 |
| 岗位列表页 | 岗位数从 2463 涨到约 3560，需要考虑是否默认折叠同族 |
| `advances_to` 相关展示 | 「下一级成长目标」终于有数据了，前端此前按「常为空」设计（`goal_overview.py:17` 记录覆盖率 1%），需复核 |

## 8. 优先级与排期

不必一次拆完 483 个。用已有的 **A 榜**（人社部《最缺工 100 个职业排行》+ 国家认定新职业，共 133 条，见 `docs/热门岗位TOP100与方法论.md`）与这 483 个求交集，先拆交集验证效果。

热度在这里的作用是**排期**，不是拆分规则——就算某岗位极度抢手，若国标给它的 5 档要求写得一模一样，拆 5 个仍然是错的。

## 9. 不要重走的路：招聘网站拿职级热度

`docs/热门岗位TOP100与方法论.md` 已于 2026-08-17 实测论证：

| 站点 | robots.txt | 结论 |
|-|-|-|
| zhipin.com | `Disallow: *?position=*` `*?city=*` `/*?query=*` | 职位搜索被明确禁止 |
| zhaopin.com | `Disallow: /*?*` `*/api/*` `/*.json*` | 所有 API 与 JSON 全禁 |

实测调 BOSS joblist 接口返回 `code:37 您的环境存在异常`（JS 挑战）。项目已定原则**不逆向、不绕验证码**。

库里 BOSS 那 821 个岗位来自**职位分类树**（`wapi/zpCommon/data/position.json`，不在 Disallow 内），只有类目名：`rank` 字段实测恒为 0，`heat_status` 全部是 `pending_calibration`（821/821 未校准），**没有薪资、经验、原始职位标题**，无法反推职级。

所以「哪个职级抢手」目前没有合规数据源。这也正是本方案改用「国标等级 + 要求形态差异」作判据的原因——**国标本身就是职级的权威定义，比从招聘数据猜更可靠，且不需要额外采集。**

## 10. BOSS 那 821 个岗位怎么办

本方案只覆盖国标岗位。BOSS 岗位没有多档素材（技能由 LLM 生成，一技能一档），也没有职级信息（132 个带 `attrs.level`，但那是 job_family 级别的粗分）。

它们的问题是另一条链——`category` 为 NULL 导致分类与先修都生成不出来，属于「体系不匹配」而非「维度丢失」，见根因文档第 3 节。**两件事不要混在一起做。**

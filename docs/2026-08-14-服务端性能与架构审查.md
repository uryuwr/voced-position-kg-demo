# 服务端性能与架构审查

范围：`backend/` 全量（72 个 Python 文件）。不是当前工作区 diff。
审查日：2026-08-14。不改代码。

分层意图是 `api/` → `kg/pg_store/` → `agent/`，但没守住：`query.py`(1781) / `biz_store.py`(1743) / `main.py`(1413) / `schemas.py`(1209) / `routes_student.py`(1011) 五个文件过了 1000 行，学员路由里有 SQL，包里还带着已经不走请求路径的 SQLite / Neo4j。上线前真正会先炸的是运营问题：每次查询新建 `psycopg.connect()`，学员读路径反复跑整份幂等 DDL，外加几处 N+1 / 全表 `attrs::json` 扫描。

## 结论

当前体量（内测、个位数并发）能跑。按「独立部署 + 真实并发」的交付标准，连接池、DDL 与鉴权三件事不过关。

## 性能 / 正确性

### 1. 无连接池，每个 helper 一次 TCP

`backend/kg/pg_store/client.py:145`

`connect()` 是裸 `psycopg.connect(DATABASE_URL)`；`session()` 每次 with 开/提交/关一条连接。`requirements.txt` 已写 `psycopg[binary,pool]`，仓库里没有 `ConnectionPool`。

一次学员列表大约 2–4 次连接（`list_nodes` + `counts_for_*` + `industries_for_occupations`）；诊断/测评更多。并发到几十人时先耗尽的是 PG `max_connections` 和握手，不是 CPU。

同型：`backend/uc/client.py:70` 每个鉴权请求 `async with httpx.AsyncClient(...)`，再建一个 HTTP 客户端。

**改法**：进程级 `psycopg_pool.ConnectionPool`，`connect()`/`session()` 只 checkout。UC 共用一个 `httpx.AsyncClient`。一个请求一条连接，往下传 `conn`。

> **复核补充 · 实测开销**（对线上 PG 与内网画像服务各跑 30 / 5 次取均值）
>
> | | 现状 | 池化 / 复用 | 浪费 |
> | --- | --- | --- | --- |
> | DB 连接 | 20.07 ms/次 | 0.95 ms/次 | **95%** |
> | HTTP 客户端 | 94.78 ms/次 | 27.61 ms/次 | **71%** |
>
> 一次学员列表开 3 条连接就白扔 57 ms。HTTP 那笔更贵——**UC 鉴权每个请求走
> 一次**，等于每个接口都在付这 67 ms。
>
> **两边都不用引新库**：
>
> - DB —— `psycopg_pool.ConnectionPool` 是 psycopg3 官方组件，
>   `requirements.txt` 里 `psycopg[binary,pool]` 的 `pool` extra 就是它，
>   装了但没用。上表 0.95 ms 就是拿它测的。
> - HTTP —— httpx **本来就带连接池**，池活在 Client 实例的生命周期里。
>   `with httpx.Client(...) as c:` 一出作用域连池一起销毁，所以每次重做
>   TCP + TLS。这不是「缺池」，是「每次把池扔了」。持有长生命周期实例即可。
>
> 三个落地坑：
>
> 1. 池是**进程级**的，多 worker 时 `max_size × worker 数` 必须小于 PG 的
>    `max_connections`
> 2. 用 gunicorn `--preload` 时，import 期建池会让 fork 出的 worker 共享同一批
>    socket；要 `open=False` + 在 lifespan 里显式 `open()`
> 3. 我们是同步栈，用 `ConnectionPool` 而非 `AsyncConnectionPool`；
>    `httpx.Client` 对同步多线程安全，`AsyncClient` 只在单个 event loop 内安全
>    ——两种栈都有，各持一个
>
> 不选 SQLAlchemy `QueuePool`（要池不要 ORM）、不选 `requests.Session`
> （已有 httpx）。PgBouncer 是基础设施层的补充，省 PG 侧 fork 开销，
> 但代码里每次 `connect()` 的往返照付，替代不了应用层池。

### 2. 学员读路径反复跑整份 DDL

`backend/kg/pg_store/biz_store.py:30`

`ensure_biz_schema()` 先 `ensure_schema()`，再执行整份 `BIZ_SCHEMA_SQL`，再循环 upsert 成就种子。热路径都在调：`get_goal` / `list_goals` / `me_summary` / 简历诊断 / 测评开场 / `generate_path` / `admin_dashboard` 等，至少 20 处。

`ensure_schema`（`client.py:162`）会重跑 `SCHEMA_SQL`，包括 `created_at` 回填 `UPDATE` 和表达式唯一索引。启动时已经跑过一次（`main.py:197-204`），而且 `except Exception: pass`，失败后每个请求再试一遍。这是目录锁 + planner 工作打在 `GET /v1/student/goal` 上。

**改法**：DDL 只在启动跑，失败就起不来。请求路径删掉 `ensure_*`。`created_at` UPDATE 挪到一次性 migrate。

### 3. 图探索与学习路径是请求级 N+1

`backend/kg/pg_store/query.py:864`

`explore_graph`（`GET /v1/graph/explore`，depth≤5，max_nodes≤2000）对每个未见邻居发 `SELECT * FROM kg_node WHERE id = %s`。depth≥1 就是一次请求上百次点查。

同型：`generate_path` 按技能循环 `_courses_for_skill_key`（`biz_store.py`），每次新连接，用 `name LIKE` + `attrs::json->>'skill_key'` 扫 `skill_level`。`profession_ladder` 在路由已经拿过 positions 之后又调一遍 `profession_positions`（详见第 17 条）。

**复核补充**：`list_neighbors`（`query.py:1315`）也是同型，而且更密。它的
主查询已经 JOIN 出了邻居节点，却对每个邻居再发一次
`SELECT * FROM kg_node WHERE id = %s`（`query.py:1368`）——`limit` 默认 100，
`direction="both"` 时自身递归两遍，一次调用最多 200 次点查。
所幸这些点查复用同一条连接，不像 `generate_path` 每次新建。

**改法**：一跳一次 `WHERE id = ANY(%s)`（`expand_neighbors` 已经这么写）。
`list_neighbors` 的主查询把 `n.*` 一起选出来，删掉二次点查。
课程按 `skill_key = ANY(...)` 批查。`profession_ladder` 吃现成列表。
通用 BFS 降到 depth≤1 或下线，走 `industry_graph` / 1-hop `expand`。

### 4. 简历技能召回全表解 JSON

`backend/agent/assessment/profile.py:38`

`WHERE type='skill_level'` 再 `position((attrs::json skill_key) in resume_text)`。没有 `skill_key` 函数索引。每次简历诊断 / 测评解析对全部已发布 skill_level 行做 seq scan + JSON parse。`list_skill_bundles` 同样 `GROUP BY` 这个表达式。

**改法**：`skill_key` 做成列（或 generated/stored）+ btree；召回打列，不要在热 WHERE 里抽 JSON。

> **复核补充**：列化只降单行成本，救不了这条谓词。`position(k in %s)` 是拿
> **每一行的 skill_key** 去简历文本里找，方向和索引相反——任何 btree 都用不上，
> 必然全扫。列化后每行从「解一次 JSON」变成「读一个列」，快但仍是 O(技能数)。
> 真正的解法是：skill_key 集合是有界的（实测 2039 个 DISTINCT）且很少变，
> 进程内缓存这份列表，召回在 Python 侧做，一次 DB 都不用查。

### 5. 唯一的 async 路由把 PDF 解析和 LLM 堵在事件循环上

`backend/api/routes_student.py:757`、`:802`

两个 `async def` 都有这个问题：

- `diag_resume_upload`（:757）同步跑 `parse_resume_bytes`（最多 20MB）和
  `create_resume_diagnosis` → LangGraph `invoke`（默认超时 120s）
- `diag_resume_extract`（:802）`await file.read()` 之后同样同步跑
  `parse_resume_bytes`。**它才是前端 demo 实际在调的那个**——测评前先抽简历
  文本走的就是这条，命中频率比 upload 高得多

并发上传会冻住 UC 鉴权和所有 async 中间件。

测评 SSE（`routes_assessment.py`）是同步生成器：`stream_report` 用 `time.sleep(1.5)` 空转最多 60s，占着 worker 线程。

**改法**：文件/LLM 留在 sync 路由，或 `asyncio.to_thread`。SSE 用条件变量，不要在还堵着 loop 的同时再 sleep 占线程。

### 6. `get_node` 不滤状态，归档节点能被学员锁成目标

`backend/kg/pg_store/query.py:1244`

`SELECT * FROM kg_node WHERE id = %s`，没有 status 谓词。项目约定：`archived` 是逻辑删除，任何接口都不能返回。

`GET /v1/nodes/{id}` 在 `_node_detail_core` 事后滤了；学员/业务按 id 取没有：`get_profession` / `get_position`、`student_position_match`、`set_goal`、诊断里的 `get_node(occupation_id)`。知道 id（或猜 `CN:occupation:…`）就能读到 archived/draft/disabled，并锁成目标、算匹配分。

> **复核订正**：初稿把 `list_neighbors` 的二次点查也算进了这条，不成立。
> 它的外层 JOIN 已经带了 `COALESCE(e.status,'published') <> 'archived'` 和
> `COALESCE(n.status,'published') <> 'archived'`，id 是从过滤后的行里出来的，
> 二次取回不可能捞到 archived 节点。它的真问题是 N+1，已并入第 3 条。
> （`draft`/`disabled` 确实没滤，但那是外层查询的口径，与二次点查无关。）

**改法**：`get_node(..., scope="public"|"manage")` 必须走 `node_published` / `node_not_archived`，成为唯一取点入口。

### 7. 鉴权关 TLS，且 `DEBUG` 等于绕过 MAC

`backend/uc/client.py:70`，`backend/settings.py:56`

UC 校验 `httpx.AsyncClient(..., verify=False)`。中间人可以伪造 200 + `user_id`。

`AUTH_DEBUG = AUTH_DEBUG or DEBUG`。任意 `DEBUG=1`（日志、k8s verbose）打开中间件旁路（`auth.py:124-202`），`X-Test-Uid` 即登录。

**改法**：`verify=True`（或显式 CA）。旁路只认 `AUTH_BYPASS`。不要把 `DEBUG` 别名成跳过 MAC。

> **复核补充 · `verify=False` 是三处，不是一处**
>
> 初稿只点了 UC。实际还有 `bts/auth.py:119`（换 token）和 `bts/client.py:92`
> （所有出站 BTS 调用），注释写的是「对齐 bcs：内网证书常不被信任」。
>
> BTS 这两处的性质和 UC 不同，得分开说：
>
> - **`app_secret` 没有泄露风险**——`build_token_request_body` 只发
>   `secret[:4] + "******"` 加一个 HMAC 签名，密钥本身不上网。这点设计是对的。
> - **但 `mac_key` 是明文回来的**。`POST /v1/tokens` 的响应体里
>   `{access_token, mac_key, expires_at}` 全明文，中间人拿到 `mac_key`
>   就能在有效期内伪造任意已签名的 BTS 请求——BTS 的 HMAC 防篡改，
>   但防不住密钥本身在未校验的通道上被读走。
> - **画像 PII 走同一条通道**。五维记忆（身份/情境/偏好/经验/活动）
>   是明文 JSON，`verify=False` 下全程可读。
>
> 「内网证书不被信任」是运维问题，解法是把内网 CA 打进镜像
> （`verify="/etc/ssl/certs/internal-ca.pem"`）或配 `SSL_CERT_FILE`，
> 不是全局关掉校验。三处要一起改，留一处等于没改。

### 8. `/health` 对全图表做 COUNT

`backend/kg/pg_store/client.py:174`

`/health` 调 `verify_connectivity`，对 `kg_node` / `kg_edge` 各 `SELECT COUNT(*)`。`/v1/stats` 和运营看板再加六组全表 `COUNT`/`GROUP BY`，每次新连接。探活定时器会周期性扫全图。

**改法**：健康检查 = `SELECT 1`。统计缓存 30–60s，或维护一行计数。

## 架构

### 9. 分层没守住，五个文件过 1000 行

`query.py`、`biz_store.py`、`main.py`、`schemas.py`、`routes_student.py`

意图是路由 + Pydantic 在 `api/`，SQL 在 `pg_store/`。现状：`main.py` 同时扛健康检查、静态页、search/explore/expand、节点边 CRUD、审核、统计；`biz_store.py` 混着匹配算法、诊断落库、学习路径、看板、DTO。`student_profile` 在路由里跑诊断/技能 SQL。`write.py` / `review.py` 每次管理端写再 `ensure_schema()`。没有请求级 unit of work：专业详情 = `get_profession` + `profession_positions` + 再算一遍 `profession_ladder` + counts，各自 `connect()`。

**改法**：`main.py` 拆成 `routes_graph.py` / `routes_kg_admin.py`（对齐 student/assessment）。`query.py` 按读模型拆（search/list vs expand vs 能力全景）。`biz_store.py` 拆 goal / diagnosis / path / match。`api/` 禁止 SQL。一请求一 `session()`，helper 吃 `conn`。

> **复核补充 · 「SQL 和业务混在一起」到底混到什么程度**
>
> 按 AST 逐函数统计（`backend/` 共 506 个函数、13547 行函数体）：
>
> | | 行数 | 占比 |
> | --- | --- | --- |
> | 纯逻辑，不碰库（**现在就能脱库测**） | 6801 | **50%** |
> | 纯取数（SQL 为主，分支 <10） | 4011 | 30% |
> | SQL + 业务真混在一起（分支 ≥10） | 2735 | **20%** |
>
> 所以「都混在一起」并不准确——一半的代码已经是干净的。混的部分集中在
> 22 个函数，且都是大块头：`explore_graph`(294 行 / 61 分支)、
> `graph_by_industry`(258)、`demote_noncompliant`(212)、
> `list_skill_bundles`(159)、`capability_by_major`(156)。
>
> 业务核心其实已经分出来了：`biz_store.match_with_profile(occ, required,
> user_levels)` 是纯函数，给数据算加权达标率，一行 SQL 都没有。它就是范本。
>
> **真正的结构缺口是另一个数字**：
>
> ```
> pg_store 里自己 connect() 的地方   103 处
> 接受外部 conn 的公开函数              5 个（还都在 migrate / ensure_schema 这类工具里）
> ```
>
> **一次请求落不进一个事务。** 专业详情要查 4 次就开 4 条连接、4 个独立事务，
> 中间任何一步失败，前面几步已经提交了。Java Repository 层真正值钱的不是
> 「藏起 SQL」，是 **Unit of Work**——N 个操作要么一起成、要么一起回滚。
> 这个我们是零。它同时也是第 1 条连接池能否真正省下 20 ms×N 的前提。
>
> #### Python 该不该照搬 Repository
>
> 「一律加 Repository」**不是 Python 的主流**，这点要说清楚，免得照着 Java
> 的样子上一层没收益的转发：
>
> - **Django** —— ActiveRecord（Model + Manager/QuerySet），没有 Repository 层，
>   业务写在 model 方法或 service 函数里。按使用量它是 Python Web 最大流派。
> - **FastAPI + SQLAlchemy** —— 常见做法是每个聚合一个薄 `crud.py`
>   （有人叫 repository），边界上用 Pydantic。是「Repository lite」，
>   没有 interface + 多实现那一套。
> - **完整 Repository + Unit of Work** —— 权威参考《Architecture Patterns with
>   Python》(Percival & Gregory)。书里自己写明：复杂度到了才上，不是默认选项。
> - **裸 SQL + 查询模块**（我们现在这样）—— 性能敏感服务里很常见，本身不是
>   反模式。
>
> 问题不在「要不要 Repository」，在**接缝切在哪**。我们已经有接缝
> （`api/` → `pg_store/`），只是接缝上漏了事务。
>
> #### 建议的改造顺序
>
> **① 传 `conn`（最高 ROI，且是连接池生效的前提）**
>
> ```python
> def get_goal(conn, user_id): ...       # 不再自己 connect()
> ```
>
> 路由层一个 `with session() as conn:` 往下传。一步解决三件事：事务边界、
> 连接池真正省下握手、以及第 12 条判分线程里的 1+N 连接。
>
> 这个模式**代码里已经在用**——`goal_overview` / `node_detail` /
> `skill_composition` / `industry_graph` 里已有 12 个 `_xxx(conn, ...)`
> 私有 helper，只是没往上贯通。所以不是引入新范式，是把已有范式贯通。
>
> **② 把那 22 个混合函数里的纯计算摘出来**
>
> `explore_graph` 的 BFS、`demote_noncompliant` 的合规判定、报告构建，
> 都不需要数据库。取数与算分分开后，那 2735 行的大部分能变成不起 PG 就能测的
> 纯函数。照 `match_with_profile` 的样子做。
>
> **③ Repository 抽象本身：不建议做**
>
> 抽象的收益是「可换数据库」和「可测试」。我们只有一个 PG 且不会换
> （CLAUDE.md 写死「数据库用线上已有实例，不由本项目部署」），
> 可测试性 ①+② 已经拿到。再套一层 interface 只是多一层转发。

### 10. 交付包里还带着两套死 store

`backend/kg/graph_store.py`，`backend/kg/neo4j_store/`

SQLite `nodes`/`edges` 和整套 Neo4j query/migrate 都在。`api/` / `agent/` / `pg_store/` / `userprofile/` 都不 import。`/health` 报 `"store": "postgresql"`。Neo4j 已从 `requirements.txt` 注释掉。但 `_rel_dict` 仍吐 `neo4j_type`，`query.py` 模块注释还写「对齐前 Neo4j 响应形」。

这不是双写 bug，是「图读走哪」有三个答案。

**改法**：SQLite + Neo4j 挪到 `crawlers/` 或 `scripts/`。镜像里删掉 `backend/kg/neo4j_store`。客户端不再读 `neo4j_type` 后从响应去掉。

### 11. 产品已经有有界读模型，却还在对外暴露通用 BFS

`backend/kg/pg_store/query.py:680`

`industry_graph` / `occupation_skills_graph` 已经限专业/岗位数并告诉前端截断了。旁边 `GET /v1/graph/explore` 仍是无向 BFS（depth 5 / 2000 点）。`main.py` 自己也说管理端列表不该再走它。这就是第 3 条 N+1 的来源，外加约 200 行路径还原。

**改法**：下线通用 BFS。留下 `search` + `POST /v1/graph/expand`（1 跳、已限 200）+ `industry_graph`。或藏到 dev flag。

## 复核补充（2026-08-14，逐条对代码验过）

初稿 11 条里 8 条属实、1 条定性有误（已在第 6 条内订正）、2 条不完整
（第 4、5 条已就地补齐）。下面是初稿没覆盖的。

### 12. 判分后台线程无上限，且线程内自己还有 N+1

`backend/agent/assessment/service.py:216`

`_grade_open_async` 每道未判问答题起一条 `threading.Thread(daemon=True)`，
没有线程池也没有并发上限——`_GRADING` 只是「同一题别重复起」的在飞标记，
不是配额。一场测评有几道开放题就起几条；多人同时结算就是几十条线程各自
调 LLM。

线程内部（`service.py:200-212`）为了拿「同技能选择题的档位上限」，
先 `store.list_answers()` 再对每条答案 `store.get_question()`——两个函数
各自 `with connect()`，于是一条判分线程要开 1+N 条连接。这是第 1、3 条
两个问题叠在同一处。

**改法**：判分入队列 + 固定大小 worker（或直接 `ThreadPoolExecutor`）。
上限基准一条 SQL 取回，别在循环里逐题查。

### 13. 判分线程是 daemon，进程重启即丢，且无补偿

同上。`daemon=True` 意味着进程退出不等它跑完。在飞的判分丢失后，
`biz_assessment_answer` 那行永远停在 `grade_status='pending'`，
全仓没有任何扫描/重跑逻辑（`grep grade_status='pending'` 只有计数用途）。

`stream_report` 有 60s 超时兜底（`service.py:229`），所以报告不会挂死，
但那道题的档位**永久丢失**，报告按「未测」处理——学员答了题却不计分，
且没有任何地方能看出来发生过这事。

**改法**：判分改成可重入的任务表（已有 `pending` 状态，缺的是取回重跑）；
结算时对超时未判的显式标 `failed` 并在报告里说明，不要静默当未测。

### 14. `_GRADING` 的 check-then-set 没有锁

`service.py:197-199` 是 `if _GRADING.get(key): return` 后 `_GRADING[key] = True`。
两步之间没有锁，同一题并发提交两次会起两条线程重复判分。dict 单次操作有
GIL 保护，但检查与写入之间没有。概率低，但重复判分会互相覆盖 `update_grade`。

**改法**：用 `dict.setdefault` 原子化，或加锁。

### 15. 技能画像缓存只在读到过期项时淘汰，且是进程内的

`backend/userprofile/skill_profile.py:24-45`

`_CACHE` 是模块级 dict + `threading.Lock`（并发安全没问题）。但淘汰只发生在
「读到一个过期条目」时；某用户缓存后再没回来，那条就常驻到进程结束。
条目本身是完整画像 dict，量级不大但只增不减。

更要紧的是它是**进程内**缓存：多 worker 部署时同一用户命中不同 worker 会
拿到不同画像，刚做完测评调 `invalidate()` 也只清得掉当前进程那一份。

**改法**：上限 + LRU；或缓存挪到 PG/Redis，`invalidate` 才是全局的。

### 16. `backend/.env` 用 `override=True`，与容器/配置中心注入冲突

`backend/settings.py:35`

`load_dotenv(backend_env, override=True)` 会**覆盖已存在的进程环境变量**。
镜像里若同时打进了 `.env`，K8s / SDP 配置中心注入的环境变量会被它盖掉，
且盖得悄无声息。`docs/SDP配置中心接入调研.md` 正在推的方向和这条直接冲突。

CLAUDE.md 把它记为约定（本地开发确实方便），但那是开发期口径；
交付形态下「外部注入优先」才是对的。

**改法**：镜像不打 `.env`；或按环境区分——检测到容器/配置中心变量时
降为 `override=False`。

### 17. `/v1/professions/{id}` 一次请求把岗位查两遍

`backend/api/routes_student.py:143-144`

路由先 `biz.profession_positions(profession_id)`，紧接着
`biz.profession_ladder(profession_id)`，而后者内部（`biz_store.py:416`）
又调了一次 `profession_positions`。同一份数据查两遍、开两条连接。

初稿第 3 条提了这个现象，但归在「学习路径 N+1」下；它其实是独立的一处
调用冗余，改起来只要给 `profession_ladder` 传入现成列表，一行的事。

### 18. 响应模型校验是新增的失败面（初稿成文后引入）

`backend/api/schemas*.py`

初稿写于 82 个端点补 `response_model` **之前**。补完之后，响应体不符合模型
会由 FastAPI 抛出 `ResponseValidationError` → 500。这把「一条脏数据打死
一整页」的风险从查询层挪到了响应层：库里出现一条越界值（比如 `level=0`、
新增的枚举值），整个列表接口直接 500。

补模型时已经跑过真实数据校准（`user_level` 放开到 0、雷达单/双系列区分等），
`tests/e2e_robustness.py` 12/12 通过，但那只覆盖了当前库里的数据形态。

**改法**：把这条纳入「脏数据不能打死一整页」的既有约定——响应模型的数值
字段按**实际可能取值**放宽，枚举优先用 `str` + 注释而非 `Literal`，
除非该枚举确实由服务端独占写入。

## 可扩展性 / 封装性 / 冗余（2026-08-14 追加）

这一轮不看性能，只看「加个东西要改几处、模块边界守没守住、有没有抄了两遍」。
结论用脚本机械扫出来，不是读代码的印象：

- `scripts/_dep_cycles.py` —— 依赖环 + 跨模块引用的私有名
- `scripts/_dup_blocks.py` —— 8 行以上完全相同的代码块（滑窗哈希）

### 19. 同一份关键词表抄了两份，而且已经漂移

`backend/agent/diagnose.py:75`、`backend/kg/pg_store/biz_store.py:768`

两处规则兜底的简历关键词表，结构、档位、分值完全一样（命中给 `level=2/score=40`，
全不命中给「通用职业素养」`level=1/score=20`），只有 evidence 文案不同。
**但两份已经不一致了**：

| | `diagnose._rule_parse` | `biz_store._SKILL_KW` |
| --- | --- | --- |
| 规则条数 | 10 | 8 |
| 开发类 | `python\|java\|开发\|编程\|C#` | `python\|java\|开发\|编程`（无 C#） |
| 汽车维修 / 航标作业 | 有 | **没有** |
| 先查技能库召回 | 有（`_kg_recall`） | **没有**，直接上关键词 |

后果是实打实的：一份写着「汽车维修」的简历，走对话诊断能命中，走简历诊断
命不中。这不是隐患，是已经发生的行为分叉——而且没有任何测试会发现它，
因为两条路径各测各的。

**改法**：关键词表与兜底档位规则收敛到一处（`agent/` 下），
`biz_store` 调它，不要自己留一份。

### 20. 五组模型定义重复，分页口径还不统一

拿 `openapi.json` 按「字段名集合」聚类，形状完全相同的模型有 5 组：

| 形状 | 重复的模型 |
| --- | --- |
| `{id, name}` | `IdName`、`IndustryLink`、`IndustryRef`、`RefOut`、`SkillCategory` |
| AI 网关状态 | `AiGatewayOut`、`AiGatewayStatus` |
| 学习目标 | `GoalItem`、`UserGoalBrief` |
| 单系列雷达 | `MatchRadarOut`、`SimpleRadar` |
| 学员技能 | `UserSkillItem`、`UserSkillOut` |

**这批绝大部分是补 `response_model` 那轮引入的**，原因是当时按「一个路由域
一个 schema 文件」切分，跨文件复用会撞循环 import（`schemas_admin` 已经
import `schemas`，反过来就成环），于是就地又定义了一个。`AiGatewayStatus`
是最典型的——它存在的唯一理由就是 `schemas.py` 不能 import `schemas_admin.py`。

分页出参也没统一：9 个列表接口用 `total_pages`，只有
`DiagnosedOccupationListOut` 用 `pages`。前端得为这一个接口写特例。

**改法**：抽一个 `schemas_common.py` 放 `{id,name}`、分页基类、状态枚举这类
公共件，其余 schema 文件单向依赖它。`DiagnosedOccupationListOut` 改继承
`PageMeta`（`pages` 保留一版做兼容字段）。

### 21. `_node_dict` 是事实上的公共 API，却起了私有名

`backend/kg/pg_store/query.py:73`

被 4 个模块、6 处 import：`node_detail`、`skill_aggregate`(×3)、`skill_write`、
`write`。同类还有 `publish_rules._set_skill_key_status`（`review`/`write` 引用 4 处）、
`query._rel_dict`。

下划线开头在 Python 里是「别从外面用」的约定。当一个私有名被四个模块依赖时，
它已经是公共契约了，只是没人敢承认——于是改它的签名没有任何保护，
IDE 的「查找引用」也会因为它看起来私有而被人忽略。

同型的还有跨层伸手：`stages.py:142` 调 `service._ctx()`，
`routes_student.py:651` 调 `sp._cached()`——路由层直接读了画像模块的私有缓存。

**改法**：`_node_dict` / `_rel_dict` 去掉下划线并在模块 `__all__` 里声明，
或挪到 `pg_store/dto.py`。`_cached` 换成 `get_profile(..., use_cache=True)`
这类正经入口，别让路由知道缓存的存在。

### 22. 三对双向依赖，112 处函数内 import

`scripts/_dep_cycles.py` 的结果：

```
kg.pg_store.publish_rules  ⇄  kg.pg_store.write
kg.pg_store.query          ⇄  kg.pg_store.skill_aggregate
userprofile                ⇄  userprofile.skill_profile
```

全靠把 import 塞进函数体来躲开——全仓 112 处函数内 `import backend.*`，
集中在 `routes_admin_biz`(16)、`routes_student`(15)、`review`(11)、
`assessment.service`(8)。`skill_aggregate.py:398` 甚至直接写了注释
`# local import avoid cycle`。

函数内 import 本身不算错（延迟加载有其用处），但 112 处、且成因是环，
说明模块职责切错了：`query` 既是底层读取又要用 `skill_aggregate` 的聚合，
`write` 既写库又要判发布门禁。

**改法**：把双向的那部分下沉成第三个模块（如 `pg_store/skill_key.py` 承载
`SKILL_KEY_SQL` 与聚合原语），让 `query` 和 `skill_aggregate` 都单向依赖它。

### 23. 同一段异常处理抄了三遍

`main.py:1154`、`main.py:1191`、`routes_admin_biz.py:222`

`CodeConflictError → 409 + detail{error,message,field,code,existing}` 逐字重复
三处。第四处（`submit_change`）虽然形状一样，注释却在解释「必须在 ValueError
之前捕获」——说明这个坑已经被踩过，但解法是复制而不是收口。

**改法**：`@app.exception_handler(CodeConflictError)` 一处注册，三处删掉。

### 24. `counts.py` 三段同构 SQL，只差关系名

`counts.py` 的 `counts_for_industries` / `counts_for_majors` / `counts_for_occupations`

「按 rel_type 统计邻居数、带发布过滤、`dst_id = ANY(%s)`、`GROUP BY` 后并回
`out`」这套写了三遍，差异只有 `rel_type`（`belongs_to` / `prepares_for`）和
JOIN 的节点类型。

**改法**：一个 `_count_by_rel(conn, ids, *, rel_type, node_type)` 收掉。

### 25. 鉴权旁路分支重复，改一处漏一处的形状

`auth.py:137`、`:190`

「没有 Authorization」和「UC 校验失败」两条路径各写了一份完全相同的旁路逻辑
（`AUTH_BYPASS or AUTH_DEBUG` → 从 `x-test-uid` 造用户）。这类重复在鉴权代码里
尤其危险：收紧旁路条件时只改一处，另一处就是留着的后门。
结合第 7 条（`DEBUG` 会打开 `AUTH_DEBUG`），这两处得一起收。

### 26. `attrs` 的 JSON 解析各写各的

`skill_composition.py:79`、`:155`、`:261`、`goal_overview.py:265`

四处各自写 `json.loads(x) if isinstance(x, str) else (x or {})`。`attrs` 是
无约束列，正是最该有统一入口的地方——现有的 `config.attrs_level_int()` 只解决了
SQL 侧的取值，Python 侧没有对应件。哪天要加「解析失败降级为空 dict 并打点」，
得找齐四处。

**改法**：`pg_store/config.py` 加 `attrs_dict(row) -> dict`，四处统一调。

### 27. 本体文件不参与运行时，加一个维度要改二十多处

`schemas/graph_schema.yaml`（6.3 KB）是声明的本体，但 **`backend/` 一行都不读它**
（`grep graph_schema backend/` 无命中）。真正的口径散在字符串字面量里：

- 节点类型枚举有两处且**不一致**：`schemas.NodeType` 是 6 个（含 course /
  credential），`review.DIM_TYPES` 是 4 个
- 按 type 分支的 `if/elif` 22 处，散在 6 个模块（`counts` / `node_detail` /
  `publish_rules` / `query` / `skill_composition` / `write`）
- 关系名以裸字符串写在 SQL 里，`query.py` 一个文件出现 44 次

加一个维度（比如「课程」真正接进四维）要动二十多处，且没有任何机制保证
YAML 与代码一致。边方向（`belongs_to` 是子→父）这类易错约定也只存在于注释里。

这里有个约束要一并考虑：按「backend 必须能独立部署」，backend 不能读仓库根的
`schemas/`。所以不是「让代码去读 YAML」，而是**本体要搬进 backend**。

**改法**：`backend/kg/ontology.py` 定义节点类型、关系类型、方向与合法端点，
`schemas.NodeType` / `review.DIM_TYPES` / SQL 里的 rel_type 全部引用它；
仓库根的 YAML 退化为文档，或由该模块生成。

### 28. `api/` 层仍有 SQL 与直连

`routes_student.py:610`

`student_profile` 里 `from ...client import connect` 并直接跑两条 SQL
（查诊断历史、查 `biz_user_skill`）。这是第 9 条「分层没守住」的具体残留点，
全仓仅此一处，收掉成本很低。

## 建议落地顺序

1. 连接池 + 启动失败即退出（1、2）—— 不改接口，立刻降握手和目录锁。
   **与「helper 吃 `conn`」（9）一起做**：只建池不传 conn，103 处仍各自
   checkout，事务边界照样没有，池的收益也只兑现一半。
2. 鉴权：`verify=True`，切断 `DEBUG`→旁路（7）。
3. `get_node` 加可见性（6）；`/health` 改 `SELECT 1`（8）。
4. 判分线程池化 + pending 可重跑（12、13）—— 学员答了题不计分是能被感知的
   业务损失，优先级高于纯性能项。
5. 批量化探索/路径/技能召回（3、4、17）；resume 两个入口离开事件循环（5）。
6. `.env` 覆盖策略（16）—— 卡在 SDP 配置中心接入前面。
7. **关键词表去重（19）**——已经在产生行为分叉，不是欠债是 bug，成本又低，
   可以插在任何位置做掉。
8. 异常处理 / 计数 SQL / 鉴权旁路 / attrs 解析四处收口（23–26）——纯删代码，
   其中 25 与第 7 条鉴权一起改。
9. 拆 god file、清死 store、下线 explore BFS（9–11）；`api/` 残留 SQL（28）。
10. 模型去重 + 分页口径统一（20）；私有名转正、缓存入口收口（21）；
    拆环（22）——这三条一起做，它们是同一个「模块边界切错了」的三个切面。
11. 本体收进 backend（27）——改动面最大，但它是「加维度」的前置；
    在第 4 个维度真正落地前做，晚了要改的地方只会更多。
12. 缓存与响应模型收尾（15、18）。

# 方案：管理台全量草稿态 —— 编辑进草稿，发布才对前台生效

> 2026-08-18 · 取代 `docs/方案-技能构成草稿态.md`（那份只覆盖技能构成）
>
> 目标：**管理台任何编辑动作都让数据进入草稿态，前台始终只看已发布内容，
> 草稿发布后前台才变。**
>
> 存储方案在评审中改过一次：初稿用影子表，实测读路径数据后改为**同表两行**。
> 改的理由见 §1.3，那段同时记着被否掉的选项，避免以后重复讨论。

## 0. 状态模型（先定这个，它决定其余一切）

> **`status` 是「版本」的属性，不是「记录」的属性。**

一条记录最多两行：**线上行**（`is_draft=false`）与**草稿行**（`is_draft=true`）。

| 行 | `status` | `is_draft` | 谁读 |
|-|-|-|-|
| 线上行 | `published` / `disabled` / `archived` | false | 前台按 published 读；管理台全看 |
| 草稿行 | **恒为 `draft`** | true | 只有管理台读 |

管理台展示的「记录状态」= **最新版本的状态**：有草稿行就是「草稿」，否则取线上行的 status。
所以编辑之后，管理台看到的就是草稿态——这正是原型要的效果。

**不要另造 `has_draft` 这类平行维度。**「这条数据有草稿」就等于「存在草稿行」。
（初稿曾设计成「线上行保持 published + 加 has_draft 标」，会出现
「既打草稿标又是发布状态」的自相矛盾，已废弃。）

### 0.1 前台为什么不需要「隐藏 draft」这条规则

BR-07 写的「`draft` 不进前台」是**单行模型的症状，不是需求本身**。
有了版本之后，前台的规则只有一条：**读已发布版本**。于是：

- 编辑中的记录 → 线上行还在、`status` 未变 → 前台照常展示旧内容，**记录不会消失**
- 从未发布过的新记录 → 只有草稿行 → 前台没有可读的已发布版本，自然不出现
- 下架 / 归档 → 线上行的 status 变了 → 前台不返回

「隐藏 draft」是这条规则的自然结果，不是要单独实现的规则。

### 0.2 关键安全不变量：草稿行的 status 恒为 `draft`

全仓约 120 处读查询已经在过滤 `status`（前台 `= 'published'`，管理台 `<> 'archived'`）。
只要草稿行的 `status` 永远是 `'draft'`，**这 120 处前台查询自动排除草稿，一处都不用改**。

反过来说：**一旦有人把「发布后应变成什么状态」写进草稿行的 `status`，草稿立刻泄漏到前台**
（草稿行 status='published' 会被前台查询命中）。所以那个意图存在单独的
`target_status` 列里，见 §2。这条不变量必须有测试锁住。

### 0.3 编辑动作不写线上行（有明确例外）

运营编辑只写草稿行，线上行由**发布**落地。但线上行仍有四类合法写入方，
它们不是运营编辑，见 §4。所以这条是「运营编辑不写线上行」，
不是「线上行只有 publish 能写」——后者太绝对，与现实不符。

## 0.4 需求收窄：只有「内容」进草稿（2026-08-19）

**进草稿的四类**：节点基础属性、边、技能构成（增删/改档/改权重/归一化）、技能自身属性。

**立即生效、永不进草稿**：停用 / 启用 / 删除（含归档软删与物理删除）。
此前实现过「归档落 `target_status='archived'` 草稿、发布才生效」和
「删除记 `target_status='deleted'`、发布时才 DELETE」，按新范围已撤销，
`deleted` 这个意图连列带代码一起删掉了 —— 不留半个死机制。

于是 `target_status` 只剩两个用途（`write._TARGET_STATUSES` 的注释里也写了同一份）：

1. **新建**：只有草稿行的记录，发布时决定落成 `published` 还是 `disabled`
2. **边的墓碑**：技能构成/关联里「移除一项」不能真删线上边（那会立刻对前台生效），
   落一条 `target_status='archived'` 的草稿边，发布时才归档

配套的两条，都是实测撞出来的：

- **停用要级联边、启用要能撤销级联**。停用节点时把两端边一起停用（修的是既有 bug：
  边 published 指向 disabled 节点 → 前台 5 项 Σ0.81 / 管理台 6 项 Σ1.00）。
  但**启用必须先恢复这批边再跑门禁** —— 边还是 disabled 的话 BR-03 判「无有效权重」，
  「停用 → 启用」直接变成死路（实测 400）。门禁不过就精确回滚那批边。
- **从未发布过的记录，删除 = 丢弃草稿**。只有草稿行时 `DELETE /v1/kg/nodes/{id}` 若只打线上行
  会 404，运营删不掉自己刚建的东西。丢弃草稿时还要连带清掉**别人单元里指向它的草稿边**，
  否则那些边永远发不出去，孤儿边闸门当场报红。

## 1. 存储：同表两行

### 1.1 为什么同表

前台的 ~120 处查询已经带状态过滤，草稿行 status='draft' 会被自动排除，
**这些查询一处都不用改**。这是同表方案最大的好处，也是评审中改变结论的直接原因。

### 1.2 代价：必须删掉两个外键

`kg_node` 主键是 `id`，而 `kg_edge` 有两个外键引用它
（`kg_edge_src_id_fkey` / `kg_edge_dst_id_fkey`）。主键改成 `(id, is_draft)` 后这两个外键无法成立，
**只能删除**——也就是放弃「边的两端一定存在」这个数据库级保证。

没有折中：PostgreSQL 的外键只能引用完整的主键或唯一约束，
**不能引用部分唯一索引**，所以 `UNIQUE(id) WHERE NOT is_draft` 保不住它。

实际后果：孤儿边从此靠应用层保证。这不是理论风险——`migrate.py` 里就有显式丢弃
端点缺失边的逻辑，说明历史上出现过。缓解见 §10.1 的闸门脚本。

### 1.3 被否掉的两个选项（避免重复讨论）

**影子表（`kg_node_draft` / `kg_edge_draft`）。** 初稿方案。前台零改动、外键保得住，
但管理台要写跨表叠加层 + 新建行 UNION，而实测管理台读路径本身就有 ~23 处要动
（§6.2），叠加比 `DISTINCT ON` 复杂得多；且两张表的列要与主表永久同步，
主表加列忘了同步会导致**发布时那一列被静默丢掉**。收益（保住外键）小于成本。

**反向影子表（线上快照表，前台读它）。** 语义最贴合「直接改 status」，
但要把 ~120 处前台查询全部改指向另一张表，风险远大于收益。直接否。

**草稿行用另一个 id（`{id}__draft`）。** 不用改主键、外键也保得住，但
① 违反 CLAUDE.md「id 用 `make_node_id` 生成、不要手拼」；
② 边 id 内嵌节点 id，发布时要重写 id；
③ 每个列表都会多出 `__draft` 行，等于把过滤问题换个地方重演。否。

## 2. DDL 迁移

```sql
-- ① 加控制列（幂等）
ALTER TABLE kg_node ADD COLUMN IF NOT EXISTS is_draft BOOLEAN NOT NULL DEFAULT false;
ALTER TABLE kg_node ADD COLUMN IF NOT EXISTS target_status TEXT;   -- 发布后线上行应变成的 status；NULL=保持不变
                                                                   -- 取值 published|disabled|archived|deleted
                                                                   -- （deleted 不是 status，是「发布时物理删除」的意图）
ALTER TABLE kg_node ADD COLUMN IF NOT EXISTS base_version INT;     -- 基于哪个已发布版本改的（并发检测）
ALTER TABLE kg_edge ADD COLUMN IF NOT EXISTS is_draft BOOLEAN NOT NULL DEFAULT false;
ALTER TABLE kg_edge ADD COLUMN IF NOT EXISTS target_status TEXT;
ALTER TABLE kg_edge ADD COLUMN IF NOT EXISTS unit_id TEXT;         -- 归属哪个发布单元，见 §3

-- ② 删外键（**不可逆的一步**，见 §1.2）
ALTER TABLE kg_edge DROP CONSTRAINT IF EXISTS kg_edge_src_id_fkey;
ALTER TABLE kg_edge DROP CONSTRAINT IF EXISTS kg_edge_dst_id_fkey;

-- ③ 换主键。ADD PRIMARY KEY 不幂等，必须先判断，否则每次启动都报错
DO $$ BEGIN
  IF NOT EXISTS (
    SELECT 1 FROM pg_index i JOIN pg_attribute a
      ON a.attrelid = i.indrelid AND a.attnum = ANY(i.indkey)
    WHERE i.indrelid = 'kg_node'::regclass AND i.indisprimary AND a.attname = 'is_draft'
  ) THEN
    ALTER TABLE kg_node DROP CONSTRAINT IF EXISTS kg_node_pkey;
    ALTER TABLE kg_node ADD PRIMARY KEY (id, is_draft);
  END IF;
END $$;
-- kg_edge 同理

-- ④ 业务编码唯一索引要排除草稿，否则改编码时草稿行与自己的线上行相撞
DROP INDEX IF EXISTS uq_kg_node_region_type_code;
CREATE UNIQUE INDEX IF NOT EXISTS uq_kg_node_region_type_code
  ON kg_node (region, type, ((attrs::json->>'code'))) WHERE ... AND NOT is_draft;

-- ⑤ 草稿查询走它
CREATE INDEX IF NOT EXISTS idx_kg_node_draft ON kg_node(id) WHERE is_draft;
CREATE INDEX IF NOT EXISTS idx_kg_edge_draft_unit ON kg_edge(unit_id) WHERE is_draft;

-- ⑥ 把 §0.2 的不变量交给数据库（实现时补上的，见下）
ALTER TABLE kg_node ADD CONSTRAINT ck_kg_node_draft_status
  CHECK (NOT is_draft OR status = 'draft');   -- kg_edge 同理
```

**⑥ 是实现期加的**：§0.2 是整个方案唯一的静默失效点，而「草稿行的 status 写错了」
在代码里查不出来（INSERT 的 status 是参数化传值）。有 CHECK 之后写错直接被库拒绝。
`ADD CONSTRAINT` 同样不幂等，要 `DO $$` 守卫；且**已有违规行时跳过而不是让 ALTER 失败**
—— 这份 DDL 在每次启动的必经路径上，失败等于服务起不来（跳过会 RAISE WARNING）。

**幂等性是硬要求**：本项目没有 migration 框架，这份 DDL **每次进程启动都会跑**
（`ensure_schema`）。`ADD PRIMARY KEY` / `ADD CONSTRAINT` 天生不幂等，必须像 ③ 那样先判断。

**锁与耗时**：换主键在 `kg_node`(35087 行) / `kg_edge`(53150 行) 上取
ACCESS EXCLUSIVE 锁并重建索引。数据量小、亚秒级，但**预生产 PG 与 bcs-ai-agent 共用**，
执行瞬间会阻塞对方。选低峰执行，别放在自动重启路径上第一次跑。

**回滚预案**：`DROP CONSTRAINT ... ADD PRIMARY KEY (id)` 前必须先
`DELETE FROM kg_node WHERE is_draft`（否则主键冲突）；再加回外键前必须先清孤儿边
（`DELETE FROM kg_edge e WHERE NOT EXISTS (SELECT 1 FROM kg_node n WHERE n.id=e.src_id)` 同理 dst）。
**回滚会丢掉所有未发布的草稿**，这一点要在执行前跟运营讲明。

### 2.1 `ON CONFLICT (id)` 要跟着改

主键变了，4 处 upsert 的冲突目标要改成 `(id, is_draft)`：
`write.py:311`、`write.py:512`、`migrate.py:155`、`migrate.py:180`。

`graph_store.py` 那两处是 **SQLite** 侧（`nodes`/`edges` 表），不受影响。

漏改的表现是 upsert 报 `there is no unique or exclusion constraint matching`——
会直接抛错而不是静默出错，属于好查的那类。

## 3. 发布单元：边归属 src 节点

技能构成是**边**不是节点字段。改岗位 A 的技能构成 = 改若干 `A -requires-> skill` 边，
发布 A 时这些边要一起生效。所以每条草稿边记 `unit_id`。

**约定 `unit_id = src_id`**，与管理台编辑入口天然一致：运营是「进入岗位 A 的编辑页，
改它的技能构成」，不存在「编辑一条游离的边」。`major -prepares_for-> occupation`
这类两端都可能有草稿的边同样归 src（从专业那边编辑对口岗位）。

**一个发布单元 = 一个节点草稿行 + 所有 `unit_id` 指向它的草稿边**，一个事务里套用。

## 4. 写入点分类（实现时最容易错的地方）

全仓 **31 处**直接写 `kg_node` / `kg_edge` 的 SQL，分布 9 个模块。
**它们不都是编辑动作**，分错会坏两种事：该草稿化的漏了 → 改动绕过草稿直接对外；
不该草稿化的做了 → 派生数据永不更新。

| 类别 | 位置 | 处置 |
|-|-|-|
| **运营编辑内容** | `write.py`（`create_node` / `patch_node` / `create_edge` / ~~`archive_node`~~（已改立即生效，见 §0.4） / `archive_edge` / `apply_node_links`）、`skill_composition.py` 3 处（含一处**裸 DELETE**，绕过了 write.py）、`skill_write.py:245` | **改成写草稿行** |
| 发布 / 审批落地 | ~~`review.py` 4 处~~（**分类错了，见下**）、`publish_rules.py` 5 处 | **保持写线上行**——它们就是发布侧 |
| 派生展示元数据 | `node_layout_meta.py` 7 处（`sort_order` / `child_count`） | **保持写线上行**：系统重算的缓存列，不是运营编辑的内容。草稿化会让布局永不更新。**但要加 `WHERE NOT is_draft`**，否则重算会把草稿行也算进排序 |
| 离线灌库 / DDL | `migrate.py` 2 处、`client.py` 2 处 | **保持写线上行**：不是管理台动作。同样要显式 `is_draft=false` |

`skill_composition.py` 那处裸 DELETE 尤其要注意：它不走 `write.py`，
只改 `write.py` 会让技能构成继续直接生效。

> **实现期纠错：`review.py` 不是审批侧，它就是运营编辑的主路径。**
> `REVIEW_REQUIRED=0`（当前默认）时，`POST /v1/admin/changes` →
> `review.submit_change` → **直接 `_apply` 写主库**，压根不进待审队列。
> 所以 `_apply` 的 create / update / delete 必须走草稿：
>
> - `_physical_delete_node` / `_physical_delete_edge` 是**裸 SQL、绕过 write.py** 的
>   物理删除，不拦住它，「删除」就是唯一一个不经草稿、立刻生效的编辑动作
> - 「删除进草稿」用 `target_status='deleted'` 表达：草稿阶段**什么都不删**，
>   线上行与它的边一个都不动，发布时才真的 DELETE。删除因此可撤销（丢弃草稿即撤销）
>   —— 草稿阶段就删掉的话，撤销无从谈起
> - `enable` / `disable` 不变（它们本身就是发布侧状态动作）；
>   `approve_change` 也不变（写线上行）

## 5. 新建

**新建 = 只有草稿行、没有线上行的记录。** 前台查 `status='published'` 查不到它，
天然不可见；管理台看到它状态为「草稿」。发布时把草稿行的 `is_draft` 置 false 即可
（同一行原地转正，不需要复制），`target_status` 决定它转成 published 还是 disabled。

这比影子表方案干净：不需要「主表 ∪ 影子表新建行」的 UNION。

> 库内已有的 `status='draft'` 节点（credential 那批）是历史遗留：它们是
> `is_draft=false` 且 `status='draft'` 的**线上行**。本机制不追溯改它们，
> 但要注意「`status='draft'` 的线上行」与「草稿行」是两回事，
> 管理台文案上要能区分，否则运营会以为那批数据有人在改。

## 6. 读路径

### 6.1 前台：零改动

~120 处已带 `status` 过滤的查询自动排除草稿行（前提是 §0.2 的不变量）。

**要补的只有 2 处**——按 id 点查且完全没有状态过滤的学员端路径：

- `goal_overview.py:242` `SELECT id, name, level, description, attrs FROM kg_node WHERE id=%s`
- `query.py:1424` `SELECT * FROM kg_node WHERE id = %s`

> **实现期修正：这句「只有 2 处」是错的，至少还有第 3 类，而且是列表接口。**
> 挂在「前台 · 图谱检索」tag 下、却用**管理台口径** `<> 'archived'` 的读路径：
> `industry_tree`（`GET /v1/industries/tree`）、`major_occupations`、`occupation_skills`、
> `industry_occupations`、`occupation_requires`。它们把 `status='draft'` / `'disabled'`
> 的**线上行**直接吐给前台（库里确实还留着那批 draft 线上行，见 §5），
> 与草稿行无关，是草稿态之前就有的洞 —— 但同一处必须一起补成 `= 'published'`。
>
> 还有一类不带状态过滤的**关联 JOIN**（`LEFT JOIN kg_node sn ON sn.id=e.src_id`
> 这种只为取名字的 JOIN，见 `list_edges` / `edge_review` / `industry_graph` 的晋升链）：
> 它们靠不上 status 不变量，端点一有草稿行，一条边就 JOIN 出两行 —— 列表里边重复、
> total 虚高、显示的还是未发布的新名字。这些点前台一律钉线上行（`config.online_only`）。

这两处**本来就是既有 bug**（审查文档第 128 条：今天已经能按 id 读到 archived 数据），
无论做不做草稿态都该补。另外 3 处无过滤点查在审核与写路径上
（`review.py:134`、`review.py:512`、`write.py:498`），属于管理台，本就该看得到草稿。

### 6.2 管理台：每个 id 只取一行，优先草稿

管理台口径是 `status <> 'archived'`，草稿行也满足，所以**同一记录会出现两行**。
必须去重，约 **23 处**（11 处走 `node_not_archived` / `edge_not_archived` 等片段，
12 处裸写 `<> 'archived'`）：

```sql
SELECT DISTINCT ON (id) *, is_draft AS has_draft
FROM kg_node
WHERE ... ORDER BY id, is_draft DESC   -- true 排前面 → 有草稿就取草稿
```

这是同表方案的主要工作量，但比影子表的跨表叠加简单：一个 `DISTINCT ON`，
不需要 LEFT JOIN、不需要 UNION、不需要在应用层合并两个 dict。

建议把它也收成一个片段函数放进 `config.py`（如 `prefer_draft(alias)`），
与 `node_published` 并列——**23 处各写一遍 `DISTINCT ON` 迟早漏**，
这个项目已经因为「过滤片段各写一份」栽过。

### 6.2.1 判定「有草稿」必须按发布单元，不能只看草稿节点行

> 实现期返工。改技能构成只产生**草稿边**（`unit_id` = 本节点 id），节点行一个字没动，
> 于是「只看有没有 `is_draft=true` 的节点行」的三处判定全部失灵：
> 管理台详情显示「已发布」、四维列表不打草稿标、运营在待发布清单里也认不出改了什么。
> 结果是运营根本不知道有改动没发出去 —— §0 的「记录状态 = 最新版本的状态」当场不成立。
>
> 口径统一成：**存在草稿节点行 OR 存在 `unit_id = 该节点 id` 的草稿边**
> （`query.unit_draft_kinds`，走两个部分索引）。同时给出 `draft_change`
> = `node` / `edges` / `both`，让运营看得出「改的是节点字段还是技能构成」。

### 6.5 前台不返回运维元数据

`version` / `version_label` / `updated_by` / `updated_by_name` / `owner` / `owner_name`
以及草稿态字段，**只在管理台口径返回**（`query._node_dict(admin=True)`）。两个理由：

1. `updated_by_name` 是内部运营人员姓名、`updated_by` 是内部 user-id，给学员端就是信息泄露
2. `version` 让「发布」改变前台响应字节 —— 发布只该改内容，V4→V5 连带把
   `/v1/node`、`/v1/nodes/{id}` 的响应也变了，「发布只影响该改的内容」就不成立，
   前端拿响应做缓存键会无谓失效

`admin` 默认 False 是刻意的：新增读路径**默认不泄露**，要给管理台看再显式打开。

### 6.6 「取技能构成」只能有一个实现

29 处独立 SQL、12 个模块，各自拼可见性口径 —— 草稿态之前一律 published，抄多份看不出来；
加了「草稿优先」这一维之后立刻分家：改完技能构成，`/v1/admin/composition` 变了，
`/v1/kg/node-detail?scope=manage` 没变，同一个管理台 scope 两个答案，
运营看着像「改了但没进草稿态」。

收敛成 `skill_aggregate.entity_skill_composition(node_id, scope=…)` 一处实现
（底层 `composition_rows` 出逐边明细，`_composition_pred(scope)` 是口径唯一真源）。
接进来的读路径：管理台详情、`/v1/admin/composition`、四维列表计数、
学员端岗位技能/构成/匹配、目标卡、能力全景。

**没收进来的三类，理由写在函数 docstring 里**：`publish_rules`（门禁只能看已发布事实，
口径固定，参数化反而会让人以为它能跟着 scope 变）、`skill_write` / `node_layout_meta`
（写侧与派生缓存）、`counts` 与能力全景热力矩阵（批量 GROUP BY，形状不同，
但**共用 `_composition_pred` 的谓词**）。

### 6.7 停用/归档节点要级联它的边

存量实测：`requires` 边是 `published`，指向的技能节点却是 `disabled` ——
前台按节点状态过滤看不到（5 项 Σ0.81），管理台口径 `<> archived` 看得到（6 项 Σ1.00），
同一个岗位两个权重和，两边都不报错。

三件事一起做：
1. **写侧根治**：`write.cascade_edge_status_draft` —— 停用/归档节点时把两端的边一起
   标成同样意图，走草稿、发布时生效。级联边的 `unit_id` 记**发起动作的那个节点**
   （不是 §3 的 src），否则运营发布了技能、边却散在别的单元里不跟着生效
2. **管理台标出异常**：`composition_rows(scope=manage)` 给这类边打 `dangling` +
   `endpoint_status`，构成页/详情页据此提示。**不在读侧偷偷过滤掉** ——
   那样运营永远看不到异常，数据只会越烂
3. **存量闸门**：`scripts/check_dangling_status_edges.py`（有则 exit 1，`--fix` 收敛）

### 6.8 每个列表页的状态列都要有接口字段兜着

技能库走的是 `/v1/admin/skills`（bundle 聚合），不是四维列表那个接口。给四维列表加
`record_status` 时漏了它，而前端写的是 `n.status || "draft"` —— 接口不返回 status，
**21074 个技能在页面上全显示「草稿」**，而草稿标记正是这个功能的核心信号，
运营完全分不清哪个技能真被自己改过。同一段代码里另一处又是 `n.status || "published"`，
同一字段两个方向相反的兜底，于是状态列写着「草稿」、按钮却按「已发布」渲染。

两条约束：

1. **接口侧**：`/v1/admin/skills` 返回 `status`（L1–L5 线上行聚合）+ `record_status`
   + `has_draft` + `draft_change`。bundle 的聚合规则：**任一档有草稿 → 整个 bundle 记 draft**
2. **前端侧**：拿不到状态显示「未知」，**绝不兜底成业务状态**。
   把「没数据」渲染成一个确定的业务结论是这个项目栽过多次的形状
   （`match_score ?? 0` 把「算不出来」显示成「完全不匹配」）。
   `recordStatusOf(n)` / `needsPublish(n)` 收成两个函数，四维与 bundle 共用

顺带一条同源的坑：**`prefer_draft` 不能用在前台口径上**。
`list_skill_bundles` 的公共分支一度也拼了 `prefer_draft`，于是一条记录有草稿时
它留下草稿行、丢掉线上行，草稿行又被 `status='published'` 滤掉 ——
**整个技能从学员端列表里消失**。前台一律 `online_only`。

### 6.3 详情与对比

管理台详情返回 `published{}` + `draft{}` 两份 + `record_status`（派生值，不落库），
供「改前 / 改后」对比。两份都从同一张表按 `is_draft` 取，一次查询即可。

### 6.4 列表内容取舍

列表**按优先草稿展示内容**（§6.2 的 `DISTINCT ON` 天然如此），所以改完名字在列表里
按新名字**搜得到**——这一点比影子表方案好，影子表下要额外做才行。

代价是列表显示的不全是线上现状。给每行的 `record_status` 打标即可区分。

## 7. 发布与丢弃

```
GET    /v1/admin/drafts                      待发布清单（运营工作台）
POST   /v1/admin/publish/node?node_id=...    发布一个单元
POST   /v1/admin/publish/batch               批量（收 node_id 列表）
DELETE /v1/admin/draft?node_id=...           丢弃草稿
```

单元发布在一个事务里按序做：

1. **BR 门禁事前校验**（`publish_rules`）——不合规直接拒、不写库。
   现在 `demote_noncompliant` 是**事后**扫描已发布出去的不合规数据；事前拦本来就该如此。
2. **并发检测**：草稿 `base_version` ≠ 线上行 `version` → **409**
   「这条数据在你编辑期间被别人发布过，请刷新后重新编辑」。不静默覆盖——
   两个运营同时改、后提交的把前一个冲掉且无人知晓，是这类后台最典型的事故。
3. **业务编码唯一性**：草稿改过 `attrs.code` 时，要对**线上行**再查一次重复
   （§2 的唯一索引排除了草稿，所以草稿之间不互斥，得在这里补）。
4. **端点存在性**：草稿边的两端在发布后必须都存在于线上行。引用了别人尚未发布的
   草稿节点 → 拒绝并说明缺哪个（外键已删，这一步是它的替代）。
5. 套用：
   - 有线上行 → 用草稿行内容更新线上行；`target_status` 非空则一并改 status
   - 无线上行（新建）→ 草稿行原地 `is_draft=false`
6. `version = version + 1`
7. 删除该单元的草稿行（新建那种是原地转正，无需删）
8. （P3）把被覆盖的旧内容写入 revision 表 → 多版本的地基

**批量发布逐个走各自的事务**：一个节点门禁不过不该拖垮其余，返回逐项结果
（成功 / 门禁不过 / 409 / 端点缺失 / 编码冲突）。

### 7.1 「只看草稿」的筛选口径 = 发布单元

`GET /v1/kg/nodes?status=draft&scope=manage` 不能只按 `status` 列筛：
改技能构成只产生草稿**边**，节点行一个字没动，按 status 筛就是 `total=0`。
实测过一次「列表不筛时显示草稿标、一点『只看草稿』全空」——
显示与筛选用了两份判断。

现在的谓词是「**自己是草稿行 / 历史 draft 线上行，或该单元有草稿边**」，
其中「有草稿边」引 `config.has_draft_edges`，与显示口径 `unit_draft_kinds` 同一份定义。
`total` 与列出的行天然一致：COUNT 与 SELECT 拼的是同一个 `where_sql`。

`status=published` / `disabled` 不用动：草稿行的 status 恒为 `'draft'`，
不会被这两个值命中，所以一条记录最多只有线上行匹配 —— 既不重复计数也不含草稿。

### 7.2 待发布工作台（管理台页面）

`/v1/admin/drafts` 是**唯一**能一次看全「还有什么没发出去」的地方：草稿按发布单元记，
四维列表是分维度看的，且「只改技能构成」的记录得先筛才看得到。所以管理台
「治理 → 待发布」页直接读它：名称 / 维度 / 改动种类（`change_label` + 边 +N/-N +
`target_status`）/ 最近编辑人 / 编辑时间，每行「发布」「丢弃」，顶部「全部发布」。

两条实现约束（都是踩出来的）：

- **发布失败必须把门禁原因显示在页面上**，不能只 toast 一句 400：
  运营看不出是 BR-03 权重没配满还是端点没发布，只能来问人。
  批量发布逐项列出 `code` 的人话 + `message`（含 `Σweight=1.0700` 这种具体数值）
- 结果横幅存在 `state.draftMsg` 里，**不能直接写进 DOM**：发布后要 `render()`
  重新拉清单，那次重建会把横幅冲掉，运营根本看不到失败原因

## 8. 与审核队列的关系

> **本轮不实现这一节。** 需求范围里不含审核功能，`REVIEW_REQUIRED` 保持现状（0=直写），
> 没有为审核分支写任何代码。下面是留给以后的设计意图。

`REVIEW_REQUIRED=1` 时，把 §7 的 **publish 动作本身**送进 `kg_change_request`，
草稿机制不动。**草稿管「内容长什么样」，审核队列管「谁批准发布」**，两件事。

审核队列通过后删记录、不留旧值，所以它不是版本仓库，不能替代草稿。

## 9. 与「多版本」的关系

同表两行只存**当前**草稿，单版本。真多版本 = §7 第 8 步落地：
发布时把被覆盖的线上内容存进 `kg_node_revision`。结构不用推倒。

当前 `kg_node.version` 只是计数器（`write.py:431` 发布时 +1），库里 35081 个节点是 V1、
只有 6 个到过 V2 以上，且**没有任何历史内容留存**——V2 覆盖 V1 后 V1 就不存在了。
所以「多版本」今天等于零。

## 10. 风险与明确取舍

### 10.1 外键删除 → 需要孤儿边闸门

新增 `scripts/check_orphan_edges.py`：扫 `kg_edge` 里 src/dst 在 `kg_node` 中不存在的边，
有则 exit 1。跑在灌库后与发布后。

判定分两层：**线上边的端点必须有线上行**（缺了就是前台会读到半截关系 → exit 1）；
草稿边允许指向「只有草稿行」的节点（新建专业顺手挂新建岗位就是这样），只统计不判失败
—— 那种情况由发布事务的端点校验按依赖顺序拦下（§7 第 4 步）。

### 10.2 §0.2 的不变量被破坏 → 草稿泄漏到前台

草稿行的 `status` 一旦不是 `'draft'`，前台查询立刻命中它。**必须有测试**：
造一个草稿行、断言所有前台读接口都看不到它。这是本方案唯一的静默失效点。

### 10.3 §4 的分类错误

尤其 `node_layout_meta`（错误草稿化 → 布局永不更新；忘加 `WHERE NOT is_draft` →
排序把草稿也算进去）与 `skill_composition` 的裸 DELETE（漏改 → 技能构成绕过草稿）。

### 10.4 直连改库绕得过

CLAUDE.md 已记「采集脚本和直连改库绕得过应用层」。缓解：闸门脚本比对线上行与最近一次发布快照。

### 10.5 离线采集不进草稿

`migrate.py` 与 crawlers 直接写线上行，这是有意的（采集不是运营编辑），
但意味着**重灌库会覆盖已发布内容且不经草稿**。已经踩过一次（技能档位回填被
`migrate --clear` 静默抹掉，见 CLAUDE.md）。且它们必须显式写 `is_draft=false`，
否则 upsert 会撞到草稿行。

### 10.6 跨单元依赖

新建专业 + 同时给它挂新建岗位，两个单元要按序发布。§7 第 4 步会拒绝并说明缺哪个，
但运营得自己排顺序——批量发布可按依赖拓扑排一次，排到 P2。

### 10.7 迁移不可逆 + 回滚丢草稿

见 §2 的回滚预案。删外键这一步无法通过 DDL 回退到「有外键」的状态，
除非先清孤儿边。执行前要备份。

## 12. 验证

- **泄漏测试**（P0，最重要）：手工插一行 `is_draft=true, status='draft'` 的节点与边，
  断言前台全部 GET 接口都看不到它、图检索也搜不到
- **核心断言**（P1）：编辑前后快照 diff —— 对前台全部 GET 接口取响应，做一组覆盖各类型的
  编辑（改名、改 attrs、加边、删边、改权重、归档、新建），再取一次，**逐字节相同**
- **管理台不重复**：编辑后列表里该记录仍只有一行，且状态为草稿
- **编辑不写线上行**：静态闸门 grep 新增的裸 SQL 写入点，比对 §4 白名单
- 并发：造 `base_version` 落后的草稿 → 发布回 409
- 门禁：构造不合规草稿（如 requires 权重和远离 1）→ 发布被拒且不写库
- 端点：草稿边指向未发布的草稿节点 → 发布被拒并指出缺哪个
- 孤儿边：`scripts/check_orphan_edges.py` 在发布后跑
- `python -X utf8 tests/e2e_robustness.py` —— 新接口参数注入越界/错类型/他人 id
- `scripts/dedupe_skill_composition_edges.py --check` —— 发布重建边后跑，
  确认没造出「同一技能多条 requires 边」（CLAUDE.md 那条约定的闸门）。
  **文档原来写的 `fix_duplicate_requires.py` 不存在**（记错了脚本名）；
  而 dry-run 有重复也 exit 0，当闸门等于没有闸门，所以实现期给它加了 `--check`。
- `scripts/verify_reload_keeps_levels.py` —— 主键变更影响 `migrate` 的 upsert，必须重跑
